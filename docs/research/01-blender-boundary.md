# Blender boundary: how Astroray 2.0 attaches to Blender 5.3 / 5.4

Date: 2026-11-14. Tags: VERIFIED (I read the primary source), REPORTED (secondary), UNVERIFIED.
Source paths below are on branch `blender-v5.3-release` of https://github.com/blender/blender unless stated. I diffed 9 engine-boundary files between that branch and `main` (5.4 alpha) on 2026-11-14; the diff was empty (list in section K).

## Question

How should the engine attach to Blender 5.3 and be ready for 5.4: a Python `RenderEngine` add-on with a native module, a Hydra render delegate, an out-of-process daemon, or something else? What does the 5.3 API give an external engine, what does Python scene access cost, how do deltas, threads and packaging work, and how likely are 5.3 to 5.4 breaks?

## Findings

### B. What `RenderEngine` provides in 5.3

All from `source/blender/makesrna/intern/rna_render.cc`. VERIFIED. Identical on `main`.

- B1. Overridable callbacks (all optional): `update(data, depsgraph)`, `render(depsgraph)`, `render_frame_finish()`, `draw(context, depsgraph)` (Image Editor), `bake(depsgraph, object, pass_type, pass_filter, width, height)`, `view_update(context, depsgraph)`, `view_draw(context, depsgraph)`, `view_pause(context)`, `view_resume(context)`, `update_script_node`, `update_render_passes(scene, view_layer)`, `update_custom_camera`.
- B2. Helpers: `tag_redraw()`, `tag_update()`, `begin_result/update_result/end_result`, `get_result`, `add_pass`, `register_pass(scene, view_layer, name, channels, chanid, type)`, `test_break()`, `update_stats`, `update_progress`, `update_memory_stats`, `report`, `error_set`, `frame_set`, `camera_shift_x`, `camera_model_matrix`, `active_view_get/set`, `bind_display_space_shader(scene)`, `unbind_display_space_shader()`, `support_display_space_shader(scene)`, `get_preview_pixel_size`, `free_blender_memory`, tile highlight calls. Properties: `is_animation`, `is_preview`, `camera_override`, `layer_override`, `resolution_x/y`, `temporary_directory`, `render` (RenderSettings), `use_highlight_tiles`.
- B3. Class flags, exactly these 13 are registered: `bl_idname`, `bl_label`, `bl_use_preview`, `bl_use_postprocess` (apply compositing), `bl_use_eevee_viewport` (EEVEE draws Material Preview), `bl_use_custom_freestyle`, `bl_use_image_save` (default true; false only valid with `bl_use_postprocess` false), `bl_use_gpu_context` (an OpenGL/GPU context for `render`), `bl_use_shading_nodes_custom` (default **true**: hides Cycles/EEVEE shader nodes in the node editor; set false to reuse Blender's native nodes), `bl_use_spherical_stereo`, `bl_use_stereo_viewport`, `bl_write_viewport_depth` (new in 5.3), `bl_use_materialx` (Hydra only).
- B4. `bl_write_viewport_depth`: the engine writes depth into the viewport framebuffer, "which should be used as is instead of doing an internal depth pass". In `draw/engines/external/external_engine.cc` the flag makes Blender set `DRW_STATE_WRITE_DEPTH | DEPTH_LESS_EQUAL` before `view_draw` and skip the grease-pencil depth prepass. VERIFIED. Python can write `gl_FragDepth` from its own shader (`GPUShaderCreateInfo.depth_write()` exists, `python/gpu/gpu_py_shader_create_info.cc`). Whether that can be combined with `bind_display_space_shader` (Blender's colour-management fragment shader) is UNVERIFIED, see spike S2.
- B5. Several engine instances coexist (viewport, F12, material previews). The official example says "Multiple instances may exist at the same time, for example for a viewport and final render" and shows `__init__` (must call `super().__init__`) and `__del__` ("stopping running render threads"). VERIFIED `doc/python_api/examples/bpy.types.RenderEngine.1.py`.
- B6. Final render sequence: F12 runs `RE_RenderFrame` inside `render_startjob`, a WM job worker thread (`editors/render/render_internal.cc`). `engine_render_view_layer` (`render/intern/engine.cc`) takes `draw_lock()` "so scene can't be edited while we read from it in this render thread", calls `type->update(engine, bmain, depsgraph)`, unlocks the UI, then calls `type->render(...)`. So `update()` is the only safe place to read Blender data; `render()` must run from an engine-side copy. VERIFIED.
- B7. Viewport sequence: the external draw engine creates the `RenderEngine` on first draw and calls `view_update` once, then `view_draw` on every region redraw, drawing in pixel space; Blender draws overlays after. `tag_redraw()` and `tag_update()` only set a plain flag bits `RE_ENGINE_DO_DRAW/DO_UPDATE` (`rna_render.cc:74-82`); a self-sustaining redraw loop is "call `tag_redraw()` from `view_draw` until converged" (Hydra C++ does exactly this, `render/hydra/viewport_engine.cc`). VERIFIED.
- B8. Viewport camera orbit/pan changes do not arrive via `depsgraph.updates`; they only trigger `view_draw`. BlendLuxCore's comment: "some actions in Blender (e.g. moving the viewport camera) do not trigger a view_update() call, but only a view_draw() call" (`engine/viewport.py`). VERIFIED. Matches the v1 camera-hash lesson in 00-recon.md.
- B9. Official guidance in the example: read Blender data "in the same thread" in `view_update`, then "typically a render thread will be started"; `view_draw` should "quickly draw ... and not perform other expensive work". VERIFIED (same example file).

### C. Incremental deltas on the Python path

From `makesrna/intern/rna_depsgraph.cc`. VERIFIED. Identical on `main`.

- C1. `Depsgraph.updates` yields `DepsgraphUpdate` with `id`, `is_updated_transform`, `is_updated_geometry`, `is_updated_shading`. `Depsgraph.id_type_updated(type)` is true "if any data-block with this type was added, updated or removed". Also `ids`, `objects`, `scene_eval`, `view_layer_eval`, `id_eval_get`, `mode` (viewport vs render).
- C2. `object_instances` carries the warning "Only use this as an iterator, never as a sequence, and do not keep any references to its items". Items expose `object`, `instance_object`, `parent`, `is_instance`, `matrix_world`, `persistent_id`, `random_id`, `particle_system`, `orco`, `uv`; all values are the evaluated copies.
- C3. Granularity is per ID and per aspect, not per vertex. A geometry flag means "re-read that object's mesh". What shipping engines do: LuxCore tests `len(updates)==1 and ID is Scene`, then `id_type_updated("OBJECT")`, then loops `updates` for `is_updated_geometry` (`export/caches/object_cache.py:910-940`); RPR collects `(id, is_updated_geometry, is_updated_transform)` sorted by ID type (`engine/viewport_engine.py:548-570`). VERIFIED.
- C4. v1 lessons that still apply (recon, REPORTED): world node-tree edits arrive as `NodeTree` updates, `diff()` style state must be consumed once per edit, and unknown update types should fall back to a full resync.

### D. Cost of Python traversal and how to avoid it

- D1. `foreach_get` has a C fast path only when the destination is a buffer whose format exactly matches the RNA raw type (`'f'` float32, `'i'` int32, etc.). With a mismatched dtype (for example float64) it silently falls back to a per-element Python-sequence path. RNA collections themselves expose no buffer protocol (`tp_as_buffer = nullptr`). VERIFIED `python/intern/bpy_rna.cc:6127-6330`, `foreach_compat_buffer`.
- D2. Any writable buffer is a valid destination, including a view over native or shared memory, so mesh data can be written once straight into engine-owned memory with no intermediate array. VERIFIED (same code uses `PyBUF_WRITABLE` generic buffers).
- D3. Bulk fields used by shipping engines: `mesh.vertices "co"`, `mesh.loop_triangles "loops"/"material_index"`, `corner_normals "vector"`, UV `data "vector"`, colour attributes. BlendLuxCore does all extraction with `foreach_get` into preallocated numpy arrays on the main thread ("Must run in the main thread (Blender API access)"), then does welding/islanding in numpy or C++ worker threads that never touch `bpy` (`export/mesh_converter.py`). VERIFIED.
- D4. Direct pointers: Malt reads Blender arrays with `ctypes` using `as_pointer()` of the first element of RNA collections and attribute data (`attributes["position"].data[0]`, `.corner_vert`, `loop_triangles[0]`, `corner_normals[0]`) plus `memmove` / a native C function; no Python loop (`BlenderMalt/MaltMeshes.py`). VERIFIED. It depends on contiguous layout and an internal dot-prefixed attribute name, so it is the most break-prone technique.
- D5. In-tree engines are not comparable: Cycles reads `Mesh` through `blender::Span` accessors (`b_mesh.corner_verts()`, `corner_tris()`, `intern/cycles/blender/mesh.cpp`); Hydra export uses `BKE_mesh`, `BLI_task` parallel loops and `ID::recalc` flags (`io/usd/hydra/mesh.cc`, `scene_index.cc`). A third-party extension has no C++ API: a Blender devtalk answer says there is no plugin C++ API and none soon (REPORTED, https://devtalk.blender.org/t/seeking-advice-on-c-development-in-blender-for-a-maya-tool-developer/40109 ).
- D6. 5.0 added the buffer protocol to `mathutils` (`Vector` exposes float32; matrices become non-contiguous buffers in numpy). VERIFIED https://developer.blender.org/docs/release_notes/5.0/python_api/ .
- D7. Mesh conversion in Python also needs `to_mesh`/evaluated meshes and edit-mode handling (mesh data is stale in Edit Mode, `info_gotchas_meshes.rst`). VERIFIED.
- D8. No measured Python-side numbers exist in the sources I read. LuxCore's forum position is that add-ons are slower than Cycles because they must use the Python API (REPORTED, https://forums.luxcorerender.org/viewtopic.php?p=11873 ). I did not measure. UNVERIFIED, spike S1.

### E. The 5.0+ inlined shader-node API

- E1. API: `Material.inline_shader_nodes()`, `Light.inline_shader_nodes()`, `World.inline_shader_nodes()` return `bpy.types.InlineShaderNodes` with one attribute, `.node_tree` (a `NodeTree`). Static constructors `InlineShaderNodes.from_material/from_light/from_world`. VERIFIED `scripts/modules/_bpy_types.py`, `python/intern/bpy_inline_shader_nodes.cc`.
- E2. What it does: groups inlined, reroutes and muted nodes removed ("simplifies export of shader nodes", 5.0 notes). Per the 5.0 notes it exists for external engines and covers closures, bundles and repeat zones; the source constant-folds constant sub-graphs (socket values are a variant of primitive values, closure zones and bundles) and unrolls repeat zones that carry closures or bundles. VERIFIED `nodes/intern/shader_nodes_inline.cc`, https://developer.blender.org/docs/release_notes/5.0/python_api/ .
- E3. Limits visible in code: the Python binding builds default `InlineShaderNodeTreeParams`, so repeat zones are always unrolled, all output targets are kept, and error messages (`r_error_messages`) are discarded; it raises `TypeError` if the datablock has no node tree. The result is a temporary `NodeTree` created without `Main` and freed with the Python object (`BKE_id_free(nullptr, ...)`). VERIFIED.
- E4. The Hydra/MaterialX exporter uses the same inliner (`nodes/shader/materialx/material.cc:69-70`), so Python and Hydra see the same simplified graph. VERIFIED.
- E5. Blender 5.3 has no native OpenPBR shader node (no such file in `nodes/shader/nodes/`). What exists is Principled BSDF exported to a MaterialX `open_pbr_surface` with approximations: anisotropy scaled by 0.7 and rotated, coat anisotropy missing, `specular` mapped as `specular_weight = specular * 2`, `thin_film_thickness * 0.001` (`nodes/shader/nodes/node_shader_bsdf_principled.cc:~730-800`). VERIFIED. This replaces the recon's "OpenPBR node maybe in 5.4" with a verified negative for 5.3; 5.4 status remains UNVERIFIED.
- E6. The inliner's folding covers constants only. Anything fed by an image texture or per-texel node stays as nodes, so an engine that evaluates the inlined graph per hit/texel avoids v1's "folding greys out everything downstream of a texture" failure (recon). My inference, not tested.

### F. Getting pixels into the viewport

- F1. Python offers no GPU-memory import. `gpu.types.GPUTexture(size, format=, data=Buffer)` and `gpu.texture.from_image` are the creation paths; the texture class has `clear/read/free` and sampler-state methods, no update-from-handle (`python/gpu/gpu_py_texture.cc`). A grep of `source/blender/python` for `native_handle` finds nothing. VERIFIED. `GPUStorageBuf` (5.3) is also a Blender-owned allocation.
- F2. `gpu.types.Buffer(format, dims, init)` wraps any buffer-protocol `init` without copying (`pygpu_buffer_make_from_data` stores the pointer and a reference to the parent). VERIFIED `python/gpu/gpu_py_buffer.cc:145-167, 425-446`. So a native/shared frame buffer reaches `GPUTexture` with exactly one host-side pass (the upload).
- F3. Shipping engines upload every present: BlendLuxCore creates `Buffer` then `GPUTexture(format RGB16F/RGBA16F)` each `draw()` (clamps >65519 first, because RGBA16F overflows to infinity), RPR does the same via `set_image` (RGBA16F) + `draw_texture_2d`. VERIFIED (`draw/viewport.py:205-235`, `engine/viewport_engine.py:1109-1119`). Malt builds the texture over a shared-memory pixel buffer with `ctypes.from_address`.
- F4. Zero-copy exists only in-tree. Cycles' `BlenderDisplayDriver` gets a native handle via `GPU_pixel_buffer_get_native_handle` and its CUDA device imports the Vulkan buffer with `cuImportExternalMemory` / `cuExternalMemoryGetMappedBuffer` (5.3; OpenGL path uses `cuGraphicsGLRegisterBuffer`). VERIFIED `intern/cycles/blender/display_driver.cpp:607-630`, `intern/cycles/device/cuda/graphics_interop.cpp:50-135`. This resolves the recon's open item (CUDA-Vulkan interop shipped for Cycles) and shows it is not reachable from a Python add-on.
- F5. Size of the unavoidable path: 1920x1080 RGBA16F is 16.6 MB (1920*1080*8 B) per present; 3840x2160 is 66 MB. Transfer cost UNVERIFIED, spike S2.
- F6. Hydra's viewport does not avoid it either (section H).
- F7. DLSS: no external-engine API found in 5.3 Python or RNA; engines must bring their own denoiser. Absence of evidence only. UNVERIFIED.

### G. Threading rules

- G1. Blender's official statement: "Python threads cause Blender to crash in hard to diagnose ways" and "no work has been done to make Blender's Python integration thread safe"; while helper threads run, "no code (including the main thread) may use bpy or any Blender API"; for independent Python work use `multiprocessing`. VERIFIED `doc/python_api/rst/info_gotchas_threading.rst`.
- G2. In practice every shipping engine runs a render thread, with `bpy` touched only on the main thread: LuxCore starts the session with `_thread.start_new_thread` (`engine/viewport.py`) and parallel numpy/C++ workers; RPR has a resolve thread and sync render thread (`engine/viewport_engine_2.py`). VERIFIED. Engine threads must be native (not Python) or must never touch `bpy`/RNA objects, and long native calls must release the GIL, otherwise `render()` on the job thread blocks Blender's UI (Python semantics; LuxCore's `parallel_argsort` comment says it "releases the GIL").
- G3. Never hold RNA/evaluated pointers beyond the callback: `object_instances` items are invalid after iteration (C2); `RenderEngine.__del__` can fire at any time when the user leaves Rendered mode, and `ReferenceError` appears when the C struct is freed while a session thread runs (LuxCore `start_session` handles it). VERIFIED.

### H. Hydra in Blender 5.x

- H1. Maturity: Blender's `HydraRenderEngine` is a Python base class over a C++ `Engine` (`render/hydra/*`, `_bpy_types.py:1623`). Blender ships exactly one delegate: Storm, as the built-in add-on `scripts/addons_core/hydra_storm` (`bl_use_gpu_context`, `bl_use_materialx = True`). The Cycles Hydra delegate source is in tree but `WITH_CYCLES_HYDRA_RENDER_DELEGATE` defaults OFF and `blender_release.cmake` only sets `WITH_HYDRA ON`, so official builds do not include it. VERIFIED.
- H2. Hydra 2.0 migration: "Render: Hydra: Migrate render delegate to use Hydra 2.0 API" merged 2026-05-27 (PR 158456); the commit says the 1.0 API "is deprecated (though not yet removed) in OpenUSD 26.xx". `scene_index.cc` exists on `blender-v5.2-release` and not on 5.1. 5.2 notes: "existing render delegates should continue to work without changes", OpenUSD abstracts between Hydra versions. VERIFIED (GitHub commit history of `io/usd/hydra/scene_index.cc`, branch listings, https://developer.blender.org/docs/release_notes/5.2/python_api/ ). The recon's "WIP PR" is out of date: it shipped in 5.2 and is in 5.3.
- H3. Export design: `Engine::sync` has a "fast path" `HydraSceneIndex` (retained scene index with flattening and material-binding scene indices) and a "slow USD export for reference" path chosen by `scene->hydra.export_method`. Updates use `ID::recalc` flags per object/material/geometry; transform-only edits re-emit just an xform overlay and dirty `xform`; instancing via instancer prototypes. VERIFIED `render/hydra/engine.cc`, `io/usd/hydra/scene_index.cc`. Deltas come to the delegate as Hydra prim added/dirtied/removed notices, produced by C++ code with direct mesh access (a performance advantage over any Python exporter).
- H4. Coverage gaps: `object_is_supported` lists mesh, surface, font, legacy curves, metaball, lamp, hair curves, volume only; point clouds (5.3 Gaussian splats are `OB_POINTCLOUD`) are not exported. VERIFIED `scene_index.cc`. Materials: Hydra gets either `UsdPreviewSurface` or, with `bl_use_materialx`, Blender's MaterialX export (E5); when the MaterialX export has no connected surface it falls back to the UsdPreviewSurface path (`io/usd/hydra/material.cc`), so a failed node mapping degrades to a much simpler material with only a log warning. VERIFIED.
- H5. USD coupling is hard. Blender builds USD monolithic (`PXR_BUILD_MONOLITHIC=ON`) with a per-version namespace `pxrBlender_v<USD_VERSION>` (e.g. `pxrBlender_v26_08`) and Vulkan/OpenGL Hgi enabled (`build_files/build_environment/cmake/usd.cmake:58-107`). USD moved 25.08 (5.1) to 26.03 (5.2) to 26.08 (5.3) (A3), so a binary delegate must be rebuilt against Blender's exact USD for every Blender release; the example registers it with `pxr.Plug.Registry().RegisterPlugins([...])` after `bpy.utils.expose_bundled_modules()` (`doc/python_api/examples/bpy.types.HydraRenderEngine.0.py`). Official builds do not ship USD headers (the dependency tree is the SDK). VERIFIED for the namespace/version coupling; the "no headers shipped" part is UNVERIFIED.
- H6. Display path: for non-Storm delegates Blender maps the delegate's `HdRenderBuffer` and calls `GPU_texture_update` each draw (`viewport_engine.cc DrawTexture::create_from_buffer`). The GPU-resident path (`GPURenderTaskDelegate`) is chosen in the `Engine` constructor (`engine.cc`) only when `RE_USE_GPU_CONTEXT` is set and `GPU_backend_get_type() == GPU_BACKEND_OPENGL`; `viewport_engine.cc` then just dispatches on `dynamic_cast<GPURenderTaskDelegate*>`. With Vulkan (the 5.3 default) even Storm takes the CPU-buffer path. VERIFIED (re-read in verification pass). Hydra therefore has the same upload as Python and no CUDA/OptiX interop.
- H7. Side channel: the only user data Blender passes to a delegate are the render-settings dict from `get_render_settings`, AOV token settings, and camera ID custom properties (`io/usd/hydra/camera_delegate.cc`). Object, light, world and material custom properties are not passed. VERIFIED (grep of `IDProperty` in `io/usd/hydra` and `render/hydra`). Astrophysics scene data (spectra, metric parameters, volume models) would need a sidecar.
- H8. Third-party delegates: AMD's BlenderUSDHydraAddon last release v3.0.0 on 2023-11-29 (REPORTED, its release is Blender 4.0 only); pablode/gatling is a Vulkan-RT delegate with MaterialX/OpenPBR whose README shows a render "using Blender's Hydra/MaterialX support" and ships as a USD plugin (REPORTED, https://github.com/pablode/gatling ); I found no Hydra performance benchmark against Cycles in Blender. UNVERIFIED.
- H9. Upside not available elsewhere: a Hydra delegate also runs in usdview, Houdini, Maya and Katana, and gets a standard MaterialX/OpenPBR material model. That is a reason to keep a USD-ingest door open, not to make Hydra the 2.0 Blender front-end (section "Recommendation").

### I. What shipping third-party integrations do (source read)

- I1. BlendLuxCore (https://github.com/LuxCoreRender/BlendLuxCore, v2.11.1 on 2026-09-20, GPL-3.0-or-later): a Blender extension (`blender_manifest.toml`, `blender_version_min = 4.5.0`, release text says 4.5 LTS and 5.2 LTS supported, other versions "usually work"). Engine and exporter are Python over `pyluxcore`, a native wheel from PyPI loaded by a `luxloader` that pip-downloads it (`_bpy_internal.extensions.wheel_manager`, permission "Need to download render engine"). Scene sync: per-ID caches (`ObjectCache`, material, world, visibility), `depsgraph.updates` diffing, mesh via `foreach_get`+numpy, C++/TBB mesh compute inside pyluxcore, viewport session restart for filmsize changes, new `GPUTexture` per draw. The 2.11.1 notes: "Improve dynamic library loading on Linux, fixes tbb-related crashes on Linux with Blender 4.5 LTS" (REPORTED by release text). VERIFIED code, REPORTED notes.
- I2. Radeon ProRender add-on (https://github.com/GPUOpen-LibrariesAndSDKs/RadeonProRenderBlenderAddon, v3.7.0 on 2026-09-10, "Now targets Blender 5.2", Windows asset only). Legacy `bl_info` add-on (`"blender": (5, 2, 0)`), not an extension; Python sync through `depsgraph.updates`/`object_instances` and `cffi` bindings (`pyrpr`); viewport frame as numpy RGBA16F then `gpu.types.Buffer` and `GPUTexture`; engine thread plus resolve thread. The release before it, 3.6.12, is dated 2025-08-21, so there was a one-year gap. VERIFIED code, GitHub release metadata.
- I3. Malt (https://github.com/bnpr/Malt, MIT): real out-of-process example. `Bridge.Client_API.Bridge` starts a `multiprocessing` "spawn" process with `listener`/`Connection` objects on `localhost` and shared buffers; the Blender side owns a `bridge` and uploads the returned pixel buffer into `GPUTexture` each draw; mesh data is pulled with `as_pointer()` and a C helper (D4). The tag `blender-5.0-last-version` (2026-03-29) exists on its releases page; I did not find why. VERIFIED code; the tag reason is UNVERIFIED.
- I4. Spectra Render by FarrasAris (Rust + Vulkan RT, Windows only, "Blender 4.0 up to 5.2 LTS", commercial intent): "custom Python add-on and an out-of-process high-speed IPC daemon", "Blender's main thread never freezes". The post gives no protocol, frame-delivery or scene-sync detail. REPORTED https://blenderartists.org/t/spectra-realtime-restir-caustics-true-spectral-engine-for-blender-rust-vulkan-addon/1655156 .
- I5. appleseed's Blender add-on (blenderseed) has had no push since 2023-08-14 and its last release is 2019 (REPORTED, GitHub repo metadata). Octane/Redshift: closed, not researched.
- I6. Common pattern across I1-I3: Python add-on owns UI/properties and the depsgraph diff; a native library owns the scene; frames cross as a CPU float buffer. None has GPU-resident display in Blender.

### J. Packaging as a Blender extension

- J1. Manifest `blender_manifest.toml` (schema 1.0.0): `id`, `version` (semver), `name`, `tagline`, `maintainer`, `type = "add-on"`, `blender_version_min`, optional `blender_version_max`, `license`, `platforms` (`windows-x64`, `windows-arm64`, `macos-x64`, `macos-arm64`, `linux-x64`), `wheels = [...]`, `[permissions]`, `[build]`. Build/validate with `blender --command extension build [--split-platforms]` / `validate`. VERIFIED https://projects.blender.org/blender/blender-manual/src/branch/main/manual/advanced/extensions/getting_started.rst .
- J2. ## Options and tradeoffs

The fork that matters is not Python vs C++ (an extension is Python either way); it is where the scene lives and who owns the process.

**(a) Python `RenderEngine` + in-process native module (LuxCore, RPR, Malt-mesh pattern).**
- For: only route to arbitrary Blender data (custom property groups on objects, lights, world, materials: needed for spectra, metrics, volume models); direct, synchronous cancel/progress API; shipping precedent for viewport and F12; headless CI via `pip install bpy`; the only build artifact is the native module (abi3 wheel).
- Against: all scene reads run in Python on the main thread (cost unmeasured, D8); the engine shares an address space with Blender's DLLs (TBB crash precedent, I1) and a native crash kills Blender and unsaved work; GIL must be released in every long call; several concurrent engine instances (viewport, F12, previews) must be supported without process-global state (B5, v1's WfContext singleton lesson); no zero-copy display (F1-F4).
- Sub-variants: a1 `foreach_get` into engine-owned memory (safe); a2 `as_pointer()` reads (fast, fragile, D4).

**(b) `HydraRenderEngine` + Hydra delegate.**
- For: Blender's C++ exporter does incremental sync (H3), instancing and MaterialX/OpenPBR material export for free; same delegate runs in usdview/Houdini/Maya/Katana; Blender promises 5.2+ delegate compatibility across Hydra versions (H2).
- Against: delegate must be built against Blender's exact monolithic USD per release (H5), a large dependency that conflicts with the short-build priority; Blender's Principled to OpenPBR mapping is lossy and RGB (E5) and you cannot ship spectral or astro data per object (H7); no GPU interop (H6); point clouds/splats unsupported by the exporter (H4); viewport passes everything through Hydra's `HdRenderBuffer`/AOV model; thin evidence of shipping delegates in Blender after 2023 (H8). An engine-side Python add-on is still needed for UI, so Hydra adds a layer rather than replacing one.

**(c) Thin Python add-on + out-of-process render daemon (Malt, Spectra).**
- For: crash and GPU-fault isolation (Blender survives engine death; a stuck CUDA context is restartable); no DLL or Python-ABI coupling; the engine builds, runs and is tested as a standalone program, which the astrophysics use case needs anyway; one daemon can serve viewport, F12 and previews with proper per-session contexts; can write scene data from `foreach_get` directly into shared memory (D2) and the frame returns through shared memory into a zero-copy `Buffer` (F2), so the frame path is no worse than (a); scene deltas become a recordable message stream usable as test fixtures without Blender.
- Against: a binary protocol, versioning, lifecycle (orphan processes, Windows job objects, firewall prompts if TCP localhost as in Malt, so prefer named shared memory/pipes), process start cost for previews, harder mid-render cancel, and a large exe in an extension (J3). Python still does the depsgraph walk, so (c) does not remove the Python traversal cost.

**(d) Other real options.**
- d1 USD/file export plus standalone renderer, no embedded viewport: fails the interactive-viewport priority; useful as a test/ingest door.
- d2 Fork or patch Blender with a Cycles-style `DisplayDriver`: the only way to get CUDA-Vulkan interop into the viewport (F4); not shippable as an extension and costs a rebase every release.
- d3 Native module calling Blender C++ internals: no supported API (D5).

Axes that decide between (a) and (c): (1) is crash isolation worth a protocol; (2) measured sync and present cost; (3) whether in-process DLL conflicts appear on 5.3 Windows; (4) multi-session behaviour. Hydra (b) trades the UI/data-model fit (H7, E5) and USD coupling (H5) for free incremental export; the evidence does not support making it the 2.0 critical path.

## Recommendation for Astroray 2.0

1. Make the Blender front-end a Python `RenderEngine` in a Blender extension (manifest, no `bl_info`), `bl_use_shading_nodes_custom = False`, targeting 5.3 with `blender_version_min` set to the lowest version CI passes (LuxCore's release notes call 5.2 an LTS, REPORTED; I did not diff the 5.2 flag set, and `bl_write_viewport_depth` is new in 5.3 and optional). Evidence: B1-B9, C1-C3, E1-E4, I1-I3, J1-J2, K1-K2. Reasons: it is the only route that carries per-object astro data and Blender-native UI; it is the proven pattern (LuxCore, RPR, Malt); the API surface is stable across 5.3/5.4 (K1).
2. Define the engine boundary as a flat, versioned scene-delta API in plain C types (create session; upload mesh/instance/material/light/world/camera deltas as arrays; start/stop; poll frame; read AOV). Keep the nanobind (abi3) layer a thin pass-through. The same API then works in-process, behind shared memory (daemon), from a USD/file loader and from tests with no Blender. Evidence: the transport is the only real difference between (a) and (c) (section Options); CLAUDE.md rule 8 already requires session-local state.
3. Start in-process with an abi3 nanobind module (smallest moving parts, fastest to a working viewport) and write the daemon decision as a measured gate, not an opinion: flip to (c) if spike S3 shows unfixable DLL conflicts with Blender's TBB/OIDN, if engine crashes in the field are not rare, or if multi-session contexts cannot be made clean. This is my call; the owner may reasonably prefer (c) now (see open questions).
4. Python side: one dirty-ID cache keyed by session ID, diff via `depsgraph.updates` + `id_type_updated`; viewport camera/navigation handled in `view_draw` by hash (B8); `foreach_get` with exact dtypes directly into engine-owned or shared memory (D1-D2); avoid `as_pointer()` tricks unless S1 shows a decisive win; do mesh conversion off the main thread in native code only; read everything in `update()`/`view_update()` and never hold RNA objects (B6, G3).
5. Materials: consume `inline_shader_nodes()` and evaluate the inlined graph in the engine's own OpenPBR implementation; do not depend on Blender's MaterialX/Hydra export (E5, E6, H4). Raise visible warnings for unsupported nodes (CLAUDE.md rule 7).
6. Display: accept one upload per present in 2.0 (F1-F3, F6); wrap the engine's frame buffer with `gpu.types.Buffer` (no copy) and create/reuse a `GPUTexture`; clamp to the RGBA16F range; implement both Vulkan (the 5.3 default, A2) and OpenGL backends via Blender's `gpu` module rather than any interop. Treat zero-copy as out of reach without a Blender patch (d2).
7. Hydra: do not build a delegate for 2.0. Keep a USD-ingest front-end on the roadmap as a second consumer of the same boundary API (standalone and usdview/Houdini), because delegate compatibility has stabilised since 5.2 (H2) but USD coupling is expensive (H5). Revisit only when the core is stable.
8. Packaging: build the extension zip with `blender --command extension build --split-platforms`, ship the native module as a `cp312-abi3-win_amd64` wheel (J2) or, if the "unmodified from PyPI" rule is enforced, as a PyPI-published wheel or plain abi3 `.pyd` files inside the extension (decide in S6), host on a self-hosted extension repository and GitHub releases (J3; no third-party render engine is on extensions.blender.org). Add Linux/macOS only if the GPU-backend decision allows.
9. CI: pytest against `pip install bpy==5.3.0` for sync/export tests; a small number of real-Blender GUI smoke tests; a version matrix that adds 5.4 as soon as `bpy 5.4` appears on PyPI (K4).
