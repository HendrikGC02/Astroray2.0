# Blender 5.3 feature surface and shader-graph evaluation strategy

Researched 2026-11-14. Tags: **VERIFIED** = I read the primary source (release notes, manual, API docs, or Blender source at tag `blender-v5.3-release`; several web pages were read through a fetch summariser, noted where it matters). **REPORTED** = secondary or search snippet. **UNVERIFIED** = my background knowledge or inference.

## Question

What must a production-capable Blender render engine handle in 5.3, in what order should Astroray 2.0 build it, and how should it evaluate arbitrary shader node graphs per shading point on CPU and GPU from one kernel source (bytecode VM, per-material codegen, MaterialX/OSL)?

## Findings

### F1. How an engine receives a shader graph (decides the whole strategy)

- Blender 5.0 added `Material/Light/World -> InlineShaderNodes`, "a new API for retrieving an inlined shader node tree to support closures, bundles and repeat zones in external render engines"; it inlines node groups and removes reroute and muted nodes. VERIFIED: https://developer.blender.org/docs/release_notes/5.0/python_api/ and https://docs.blender.org/api/5.3/bpy.types.InlineShaderNodes.html
- API shape: `material.inline_shader_nodes()` (no parameters, so no target-engine choice), plus static `from_material/from_light/from_world`; `.node_tree` is only valid while the `InlineShaderNodes` object is alive, otherwise "Blender can crash from a dangling pointer". Call it on the evaluated material so Geometry Nodes edits are included. VERIFIED: same API page, and https://docs.blender.org/api/5.3/bpy.types.Material.html
- Cycles itself consumes the same inliner in C++ (`inline_shader_node_tree`, `target_engine_ = SHD_OUTPUT_CYCLES`, `allow_preserving_repeat_zones = false`, so repeat zones are unrolled). The inliner also takes `target_engine_`, default `SHD_OUTPUT_ALL`. VERIFIED: https://raw.githubusercontent.com/blender/blender/blender-v5.3-release/intern/cycles/blender/shader.cpp and https://raw.githubusercontent.com/blender/blender/blender-v5.3-release/source/blender/nodes/NOD_shader_nodes_inline.hh
- The Python API page shows `from_material/from_light/from_world` plus `node_tree`, with no `target_engine` argument; the inliner struct default is `SHD_OUTPUT_ALL`. Which Material Output node the Python path picks when outputs are tagged "Cycles" vs "EEVEE" vs "All" is UNVERIFIED (spike item; `rna_*` implementation not located).
- Shader nodes gained closures with recursion, bundles, repeat zones (fixed iteration count in Cycles, dynamic in EEVEE), Menu Switch, and seven Geometry-Nodes-origin nodes (Index Switch, Switch, Boolean Math, Integer Math, Warning, Enable Output, String nodes). VERIFIED: https://developer.blender.org/docs/release_notes/5.0/rendering/ and https://developer.blender.org/docs/release_notes/5.3/rendering/
- Engine registration trap: `bl_use_shading_nodes_custom` defaults to **True**, which hides the Cycles/EEVEE shading nodes in the node editor; Astroray must set it False to expose the standard nodes. VERIFIED (source): https://raw.githubusercontent.com/blender/blender/blender-v5.3-release/source/blender/makesrna/intern/rna_render.cc
- `Use Nodes` was removed for Materials and Worlds in 5.0 (always nodes). VERIFIED: 5.0 rendering notes above.
- Principled BSDF in 5.3 "is based on the OpenPBR Surface model and is compatible with Disney and Standard Surface parameters"; it has a Thin Wall input (5.2), Dispersion (5.3), thin-film iridescence (5.0), and Cycles-only subsurface IOR/anisotropy, Random Walk SSS, specular anisotropy, diffuse roughness. VERIFIED: https://docs.blender.org/manual/en/5.3/render/shader_nodes/shader/principled.html, https://developer.blender.org/docs/release_notes/5.2/rendering/, https://developer.blender.org/docs/release_notes/5.3/cycles/, https://developer.blender.org/docs/release_notes/5.0/cycles/

### F2. The node set (what must be classified)

- Cycles' Blender-side sync matches about 90 `ShaderNode*` types (re-check: ~92 `is_type("ShaderNode...")` hits, 2 of them `ShaderNodeMix` helper checks) plus a few more (Scene Time arrives as `GeometryNodeInputSceneTime`). Absent from Cycles: Specular BSDF (EEVEE), Shader to RGB (EEVEE), Light Accumulation/Evaluation/Info, Shadow Raycast, Light Output (EEVEE "Material Lighting Nodes", new in 5.3). VERIFIED: `intern/cycles/blender/shader.cpp` above, plus https://developer.blender.org/docs/release_notes/5.3/eevee/ and file list https://github.com/blender/blender/tree/blender-v5.3-release/source/blender/nodes/shader/nodes
- Manual 5.3 node inventory (Input 24 incl. constant nodes; Output 6; Shader 25; Displacement 4; Texture 13; Color 14; Vector 15; Math 7; text nodes 12; Bundle/Closure/Repeat/Switch utilities). VERIFIED (sidebar read through summariser): https://docs.blender.org/manual/en/5.3/render/shader_nodes/index.html
- Nodes new since the v1 audit's Blender 5.2 baseline that affect scope: Gabor texture, Radial Tiling, Raycast (+ attribute sampling in 5.2), Ray Portal BSDF, Metallic BSDF, Sheen BSDF, Volume Coefficients, Point Info, Combine/Separate Cylindrical/Spherical, Mix Vector, Get Vector Component. Point Density was removed in 5.0. VERIFIED: manual list, 5.0 and 5.2 notes above.
- Raycast, Bevel, Ambient Occlusion are "raytrace-only" in the Cycles SVM; on OptiX-OSL they do not work. VERIFIED: `intern/cycles/kernel/svm/svm.h` (`__SHADER_RAYTRACE__`), https://raw.githubusercontent.com/blender/blender/blender-v5.3-release/intern/cycles/kernel/svm/svm.h ; REPORTED (OSL manual snippet): https://docs.blender.org/manual/en/latest/render/cycles/osl/index.html
- Blender's own MaterialX export (used by Hydra delegates) has a hook in 70 of the 100 node source files (30 have none, a few of those are internal helpers or EEVEE-only); several hooks are stubs that return defaults: Light Path, Wireframe, Raycast, Bevel (passthrough), AO (commented crash). **No MaterialX export** for: Voronoi, Brick, Magic, Gabor, Sky, Radial Tiling, Wavelength, Background, Hair/Principled Hair, Toon, Holdout, IES, Volume Absorption/Scatter/Coefficients/Info/Principled, AOV Output, World Output, Script, Shader to RGB, Mix (RGB legacy). VERIFIED (I grepped every `node_shader_*.cc` for `NODE_SHADER_MATERIALX_BEGIN` and read stubs): https://github.com/blender/blender/tree/blender-v5.3-release/source/blender/nodes/shader/materialx

### F3. How production engines evaluate graphs

- **Cycles SVM**: bytecode, one `switch` loop per shading point, `float stack[SVM_STACK_SIZE]` with `SVM_STACK_SIZE` 255, `SVMStackOffset` is `uint8_t`; entry points for surface/volume/displacement via `NODE_SHADER_JUMP`; bump re-evaluation via `NODE_ENTER_BUMP_EVAL/LEAVE_BUMP_EVAL`; `_DERIVATIVE` variants of nodes; closures written into `ShaderData::closure[MAX_CLOSURE]`, `MAX_CLOSURE` 64; compile-time `node_feature_mask` gates node cases. SVM runs on all backends (CPU, CUDA/OptiX, HIP, Metal, oneAPI) and is "the native representation of all Blender shader nodes". VERIFIED: `svm.h`, `svm/types.h`, `kernel/types.h` at `blender-v5.3-release`; Blender talk slides (Herholz, Siddi, 2026) https://hosted-files.sched.co/osd2026/94/Adopting%20Open%20Standards%20Blenders%20Journey%20on%20Supporting%20OpenPBR-Sebastian_Herholz_Francesco_Siddi%281%29.pdf
- **Cycles OSL**: optional, CPU and OptiX only, "All shader nodes re-implement in OSL" (slides). Manual 5.3: OSL on GPU only via OptiX; limits are constant texture filenames, no Cell/Simplex/Gabor noise, no functional `trace` (so no AO/Bevel). VERIFIED (5.3 manual https://docs.blender.org/manual/en/5.3/render/cycles/osl/index.html; 3.5 notes https://developer.blender.org/docs/release_notes/3.5/cycles/). CORRECTED: the 5.3 manual and 3.5 notes contain NO statement that OSL is slower than SVM; the "slower than built-in nodes" quote is unconfirmed for 5.3 (UNVERIFIED, older-manual snippet only).
- **Blender OpenPBR work**: Cycles has an OSL OpenPBR path (MaterialX graph -> OSL via OSLCodeGen) and a clean-room SVM implementation written "word-by-word" to the v1.1.1 spec; the two differ visibly (e.g. Tint-82, layering) and neither is yet known to be correct. OSLCodeGen "cannot fully translate MaterialX to OSL closures"; the MaterialX OpenPBR graph "does not fully cover the spec". Current spec version cited: v1.1.1. Outlook: "MaterialX and better USD support are future plans". VERIFIED (slides 18, 22-34, 42, 47-49).
- **EEVEE**: per-material GLSL generated from the node tree (`gpu_codegen.cc`, "Convert material node-trees to GLSL"). VERIFIED (file header): https://raw.githubusercontent.com/blender/blender/blender-v5.3-release/source/blender/gpu/intern/gpu_codegen.cc
- **Karma XPU** (OptiX + Embree, MaterialX only) builds device-specific shader code and pauses at scene load. REPORTED: https://sidefx.com/docs/houdini/solaris/karma_xpu.html (search snippet).
- **NVIDIA MDL SDK** generates CUDA PTX and LLVM-IR from compiled materials. REPORTED: https://github.com/NVIDIA/MDL-SDK
- **Runtime compile tools**: NVRTC compiles CUDA C++ strings at run time to PTX/CUBIN/LTO-IR/OptiX-IR, needs no nvcc on the user machine, has `-Ofast-compile`, `--split-compile`, PCH since CUDA 12.8. VERIFIED: https://docs.nvidia.com/cuda/nvrtc/index.html. Slang CPU target "functional, but not feature- or performance-complete"; CUDA/OptiX "work in progress". VERIFIED: https://shader-slang.org/slang/user-guide/targets.html
- **MaterialX codegen** targets GLSL, OSL, MDL, MSL, and recently Slang; 1.39.x ships an OpenPBR Surface node and Standard Surface translation graphs. REPORTED (search snippets only): https://github.com/AcademySoftwareFoundation/MaterialX
- **Licences of node maths** (borrowable with attribution if the engine licence allows): Cycles `svm/` node implementations (voronoi, gabor, wave, brick, magic, mapping, ies, radial_tiling, fractal_noise, mix, sky) are Apache-2.0; `svm/noise.h` is BSD-3-Clause; the multiple-scattering sky (`intern/sky/source/sky_multiple_scattering.cpp`, Fernando Garcia Linan, 4 hero wavelengths, transmittance LUT precomputed on CPU) is MIT; `sky_single_scattering.cpp` is Apache-2.0 but `sky_math.h` is GPL-2.0-or-later (re-read in verification). `sky_nishita.h` could not be located at `intern/sky/source/` in the re-check (404): treat its GPL status as UNVERIFIED and assume GPL until found. VERIFIED (SPDX headers read): `blender-v5.3-release/intern/cycles/kernel/svm/*.h`, `intern/sky/`.

### F4. Objects and geometry (what Python exposes)

- Mesh: `loop_triangles`, `loop_triangle_polygons`, `calc_loop_triangles()`, `vertex_normals`, `corner_normals`, `polygon_normals`, `uv_layers`, `attributes`, `color_attributes`, `calc_tangents()`, `sharp_face` via `shade_flat/shade_smooth`. VERIFIED: https://docs.blender.org/api/5.3/bpy.types.Mesh.html
- Instances: `Depsgraph.object_instances` is an iterator only ("never as a sequence"); `DepsgraphObjectInstance` has `is_instance`, `instance_object`, `matrix_world`, `persistent_id` ("inter-frame matching of objects with motion blur"), `random_id`, `parent`, `particle_system`. Depsgraph exposes `updates`, `id_type_updated`, `id_eval_get`, `mode` (VIEWPORT/RENDER). VERIFIED: https://docs.blender.org/api/5.3/bpy.types.Depsgraph.html and `.../bpy.types.DepsgraphObjectInstance.html`
- Curves/hair: `Curves.curves`, `.points`, `.attributes`, `.surface`, `.surface_uv_map`, `add_curves`, `set_types`. Cycles 5.0 added a "Linear 3D Curves" render option. VERIFIED: https://docs.blender.org/api/5.3/bpy.types.Curves.html, 5.0 Cycles notes.
- Point clouds: `PointCloud.points`, `.attributes`, `.type` enum (default `POINTS`); the splat enum value was not readable. VERIFIED: https://docs.blender.org/api/5.3/bpy.types.PointCloud.html
- Gaussian splats (5.3): stored as a point cloud with attributes `scale`, `rotation`, `radiance:base` (DC colour + opacity), `radiance:sh_{index}`; PLY/SPZ import only, no export; Workbench/EEVEE/Cycles render them with a default Emission shader, "performance is not ideal", assumed sRGB-trained so "not fully accurate" in linear renderers; `Apply Transform` ignores the new attributes. VERIFIED: https://developer.blender.org/docs/release_notes/5.3/rendering/ . Cycles kernel method (ellipsoid test, sorting, stochastic opacity) not found.
- Volumes: Python gives `Volume.grids` (per grid `name`, `data_type`, `channels`, `matrix_object`, `load()/unload()`), `velocity_grid*`, `velocity_scale`; **no voxel read API**. The only bulk route found is `VolumeGrids.save(filepath)` to a `.vdb`, then read natively. VERIFIED: https://docs.blender.org/api/5.3/bpy.types.Volume.html, `.../bpy.types.VolumeGrid.html`, `.../bpy.types.VolumeGrids.html`
- Cycles volumes: unbiased null-scattering default since 5.0; smoke/fire render with NanoVDB. VERIFIED: 5.0 Cycles notes. Geometry Nodes 5.3 adds grid nodes (Rasterize Points, Poisson Solver, Sample Grid). VERIFIED: https://developer.blender.org/docs/release_notes/5.3/geometry_nodes/

### F5. Lights, world, camera

- Light types are Point, Spot, Sun, Area (shapes Rectangle, Square, Ellipse, Disk); common properties `color`, `exposure`, `temperature/use_temperature`, `normalize`, `use_shadow`; sun strength in W/m2, others in W when normalised. VERIFIED: https://docs.blender.org/manual/en/5.3/render/lights/light_object.html and https://docs.blender.org/api/5.3/bpy.types.Light.html . Per-light Cycles options (portal, max bounces, MIS, caustics) and IES: UNVERIFIED for 5.3 beyond the existence of `ShaderNodeTexIES` (VERIFIED in `shader.cpp`).
- Light and shadow linking: emitter owns receiver and blocker collections; Blender inverts to bitmasks at depsgraph time, each unique set gets a bit; Cycles builds one light tree per light set; shadow linking with BSDF-sampled MIS traces an extra shadow ray. Emissive meshes support linking in Cycles only. VERIFIED: https://developer.blender.org/docs/features/cycles/light_linking/ ; REPORTED: https://docs.blender.org/manual/en/latest/render/lights/light_linking.html

- Camera `type`: PERSP, ORTHO, PANO, CUSTOM (custom shader, OSL-based). `panorama_type`: EQUIRECTANGULAR, EQUIANGULAR_CUBEMAP_FACE, MIRRORBALL, FISHEYE_EQUIDISTANT, FISHEYE_EQUISOLID, FISHEYE_LENS_POLYNOMIAL, CENTRAL_CYLINDRICAL, with latitude/longitude ranges; DOF on `CameraDOFSettings`; `shift_x/y`, `sensor_fit`. ### F7. v1 evidence (read-only, recorded numbers)

- Last mechanical audit (Blender 5.2): 152 SUPPORTED / 35 APPROXIMATED / 340 DROPPED-SILENT of 527 sockets; raw socket count judged the wrong metric, replaced by a frequency-weighted target (>= 95% weighted over ~50 scenes, zero silent drops). Weighted coverage then: gate population 0.4185 (297 uses), production corpus 0.7686 (71 uses). Source: v1 `.astroray_plan/docs/blender-coverage-reaudit-2026-09.md`, `north-star-and-integration-gate-2026-09-07.md`, `pkg310-production-corpus-burndown.md`.
- Production node corpus (8 Cycles-5.2 materials): 0/8 passing on CPU and GPU at baseline, 1/8 after the first fix wave; 39 silent (material, node, socket) pairs at baseline, 7 real after the matrix was fixed. Causes: texture-fed nodes constant-folded to grey (Mapping, Math, Color Ramp, Noise Vector inputs), Voronoi flake bump dropped, Light Path -> Mix Shader unsupported, Add Shader unsupported.
- The v1 op-VM was bolted on later (`shader_vm_compiler.py`): constant-fold first, VM only "downstream of an image texture", bounded program size, `VMCompileError` falls back to fold plus a degradation entry; opcode enums hand-mirrored in `include/astroray/shader_vm.h`; Light Path Is-Diffuse/Is-Glossy depth outputs approximate because the engine classes bounces per material, not per closure. Object-space procedurals were baked to a 64^3 grid on GPU (6.7% vs 3.7% seed noise on marble, 16.4% vs 5.5% on wood). `degradation.py` (134 LOC) is a clean pure collector with three dispositions (approximated, degraded, ignored), de-duplicated per render.
- Lesson: the failure was not "VM is wrong", it was "VM is the second path". Every socket that bypassed it was silently wrong.

## Options and tradeoffs

Axes that actually separate the options: (1) does a material edit cost a compile or only a data upload (viewport priority); (2) does CPU use the same mechanism (one-source rule); (3) backend portability (undecided GPU choice); (4) build time and dependency weight; (5) peak shading speed.

**A. Bytecode VM, single opcode table (Cycles SVM model).** Host lowers the inlined graph to a flat program; the kernel interprets it. Material edit = re-upload bytes. One interpreter source compiled for CPU and GPU. Backend-neutral (Cycles runs it on five backends). Cost: interpretive overhead, divergence between materials in a warp (mitigated by material-sorted shading), per-thread stack (SVM uses up to 255 floats), and every node's code compiled into the kernel (build time grows with node count; Cycles mitigates with `node_feature_mask`). Peak speed unmeasured here.

**B. Per-material codegen (EEVEE GLSL, Karma XPU, MDL).** Fastest steady-state (constant folding, dead-branch removal). Costs: runtime compile on every edit (NVRTC supports it on NVIDIA; Karma reports pauses), a compiler on every target including CPU (one-source rule forces a CPU JIT or bundled compiler; Slang CPU target is not performance-complete), a cache and invalidation layer, OptiX module/pipeline relink, and a hard backend lock-in for the codegen target. Heavier simplicity cost than A.

**C. MaterialX or OSL as the runtime.** Standard interchange, OpenPBR reference graph exists. Costs: Blender's own MaterialX export has no hook for 30 of 100 node files (incl. Voronoi, Sky, volumes, hair) and stubs more (F2), so it inherits Blender's gaps; OSL GPU is OptiX-only with documented limits (the "slower than SVM" claim is unconfirmed for 5.3); large dependencies (MaterialX, OSL, LLVM) against the short-build priority; spectral nodes need custom MaterialX nodes; Blender's own OpenPBR comparison shows the pipeline still disagrees with itself. Fits as a test oracle for OpenPBR, not as a runtime.

**D. A with specialisation hooks.** Same as A, plus (i) host-side constant folding (a material of only constants skips the VM), (ii) compile-time node-feature masks for kernel variants, (iii) an optional later codegen tier for hot materials if a spike proves the VM is the bottleneck. This is a refinement of A, not a separate bet.

**E. Pre-bake procedural graphs to textures.** Only for object-space cases; v1 measured it as lossy. Not a general strategy.

Real fork on the feature side: whether Blender nodes are the source of truth (inline API, full surface) or USD/Hydra MaterialX is (small surface, F2). The inline API route keeps every node reachable; Hydra route belongs to the integration workstream.

## Recommendation for Astroray 2.0

**1. Shader strategy: VM from day one, as the only path (option D).** Evidence: Cycles runs one SVM on all backends in production (F3); our priorities (edit = upload, one kernel source, short builds, backend undecided) all favour A; v1's failures came from VM-as-afterthought (F7). Rules:
- One opcode table (X-macro) generates the host lowering enums, the interpreter `switch`, and the constant folder, so there is no hand-mirrored header (v1 mirrored enums by hand).
- Every Blender node lowers through the VM; a node that cannot lower raises a visible error with node name and socket and renders magenta (CLAUDE.md rule 7; reuse the v1 `degradation.py` shape: approximated/degraded/ignored, once per render).
- Entry points surface/volume/displacement, bump re-evaluation opcodes, and derivative-aware texture sampling are in the design from the start (SVM has them for a reason).
- Closures: the program emits a bounded closure set (Cycles: 64 slots, `CAUSTICS_MAX_CLOSURE` 4). Closure/bundle/repeat features arrive already unrolled by `inline_shader_nodes()`.
- Do not adopt MaterialX/OSL as runtime; use the MaterialX OpenPBR graph and Adobe's reference implementation as test oracles (Blender's slides show both are still imperfect, so treat disagreement as "investigate spec", not "bug").

**2. Receive graphs through `inline_shader_nodes()` only.** Never walk raw node trees (the v1 translator walked them and lost groups, reroutes, mutes). Copy the tree into native structures inside the call and drop the Python object immediately (dangling-pointer warning).

**3. Material model: OpenPBR Surface v1.1.1 internally, Blender Principled as the input dialect.** Blender documents Principled as OpenPBR-based; Cycles' own OpenPBR work targets v1.1.1. Map Principled/Metallic/Glass/Diffuse/Glossy/etc. onto the one model; legacy closures become presets of it. Pin the spec commit.

**4. Honour the file working space from W0.** RGB assets and outputs are in Rec.709, Rec.2020 or ACEScg per file (5.0). RGB-to-spectrum upsampling and spectrum-to-RGB output must use the working-space primaries, including Blackbody/Wavelength nodes (Blender derives blackbody chromaticities from the config). A spectral engine that hard-codes Rec.709 is wrong for ACEScg files.

**5. Order of work (exit criterion for each is a render checked by eye plus an analytic or spec test):**
- **W0 skeleton**: mesh + instances, constant Principled (OpenPBR), point/sun/area, world colour, perspective camera, passes Combined/Depth/Normal, Blackman-Harris filter, output in working space, loud unsupported-feature report. Proves sync, VM plumbing, viewport.
- **W1 first usable release (surface renderer)**: full surface node table below at tier W1; image textures incl. UDIM and colour spaces, procedurals; spot, emissive meshes, HDRI importance sampling, Sky (multiple scattering); ortho + DOF; Mist/Index/Diffuse-Glossy-Transmission-Emission-Environment passes, Denoising Data + OIDN/OptiX (denoise workstream); adaptive sampling; transparent film; viewport edits via VM upload.
- **W2 production breadth**: volumes (homogeneous, VDB via `VolumeGrids.save`, world volume), hair/curves + hair BSDFs, SSS, Raycast/Bevel/AO/Wireframe (need in-shader ray queries), true displacement + vector displacement, point clouds, light/shadow linking, IES, portal lights, shadow catcher/holdout, motion blur (via `frame_set`, `persistent_id`), panoramic cameras, Cryptomatte, Shader AOV + light groups, Principled thin-film/dispersion polish.
- **W3 tail**: bake, Gaussian splats, OSL Script node, custom OSL camera, stereo, Toon, Ray Portal BSDF, Preetham/Hosek sky.
- Astro note: Blackbody and Wavelength nodes and volume emission are cheap and central to the destination; if the owner wants an astro demo early, volumes move into W1 (see questions).

## What a measurement spike must settle

All numbers below are to be measured on the RTX 5070 Ti and 8c/16t CPU; thresholds are for the lead to set before measuring.
1. **VM vs specialised code**: one interpreter source vs hand-specialised functions for three materials (constant Principled; Principled + image; Principled + noise -> ramp -> bump), single-material and 8-materials-interleaved frames. Report shade-stage time, registers, local-memory bytes per thread, CPU time. Decides whether the optional codegen tier is ever needed.
2. **Runtime compile cost** of the same materials via NVRTC (`-Ofast-compile`, OptiX-IR) and, for CPU, the cheapest viable route; compare with VM upload time. Decides option B outright if it costs seconds per edit.
3. **Build cost of the VM**: clean and incremental compile time of an interpreter with ~100 opcodes; incremental time after adding one opcode (budget in CLAUDE.md: 30 s incremental, 5 min clean).
4. **Inliner behaviour** on a corpus of public .blend/material assets: node-type frequency histogram (sets W1 membership), which Material Output node is chosen, group/repeat/closure/bundle/menu-switch handling, error messages, cost of `inline_shader_nodes()` for 1000 materials.
5. **Python-side data access cost**: `VolumeGrids.save` round trip for a 256^3 grid and a GN-built grid; `object_instances` iteration at 100k instances; curves/point-cloud/splat attribute readout speed.
6. **Cryptomatte** manifest written with `stamp_data_add_field` accepted by the compositor Cryptomatte node.
7. **Working space**: an ACEScg and a Rec.2020 .blend rendered with a known albedo/emission chart; spectral round trip error vs analytic.
8. **Spec check**: OpenPBR v1.1.1 changelog since 1.1 and a furnace test per lobe, against the MaterialX reference graph, before the lobe set is frozen.
