# Kernel language and GPU backend for single-source kernels

Date: 2026-11-14. Workstream: kernel-language-backend.
Tags: VERIFIED = I read the primary source (docs, source file, slide deck, forum post itself). REPORTED = secondary source or search snippet only. UNVERIFIED = inference or not found.

## Question

Which language and backend should Astroray 2.0's single-source kernels use, given: one kernel source for CPU and GPU, physics + OpenPBR correctness, Blender 5.3 (ready for 5.4), RTX 5070 Ti (sm_120) as primary hardware, and owner priorities of a fast interactive viewport, short builds, fast tests and a simple design? Specifically: how to avoid v1's nvcc register saturation (shade kernels at REG:254) and 30-minute kernel builds, and whether to go NVIDIA-only or vendor-neutral.

## Findings

### F1. How Cycles and pbrt-v4 actually do single-source C++

Cycles (Blender main, Apache-2.0 kernel):
- One kernel tree, one macro layer per backend. `ccl_device` becomes `__device__ __inline__`, `ccl_global`/`ccl_private` expand to nothing on CUDA, thread indexing and `ccl_gpu_ballot` wrap CUDA built-ins, some `sinf/cosf/expf` are redefined to fast intrinsics. VERIFIED https://raw.githubusercontent.com/blender/blender/main/intern/cycles/kernel/device/cuda/compat.h
- Backends are subdirectories `cpu, cuda, hip, hiprt, metal, oneapi, optix` under one kernel CMake. VERIFIED https://raw.githubusercontent.com/blender/blender/main/intern/cycles/kernel/CMakeLists.txt
- The same `kernel.h` declares the ~18 integrator kernels plus queue/sort/compaction/film/denoise kernels (about 75 total by my count) for all GPU backends, with per-backend `#ifdef` carve-outs (HIPRT excludes the intersect kernels; oneAPI wraps them). VERIFIED https://raw.githubusercontent.com/blender/blender/main/intern/cycles/kernel/device/gpu/kernel.h
- Register control is explicit launch bounds: `ccl_gpu_kernel(block, regs)` expands to `__launch_bounds__(block, 65536/(block*regs))`. For the `__CUDA_ARCH__ <= 1299` branch (7.x, 8.x, 12.x; 9.x-11.x are not named but fall in the same branch) the constants are 384 threads and 168 registers (255 is the hardware limit); these are the defaults passed through `ccl_gpu_kernel`, so Blackwell consumer parts fall inside it. Re-verified 2026-11-14. VERIFIED https://raw.githubusercontent.com/blender/blender/main/intern/cycles/kernel/device/cuda/config.h
- Build: CUDA kernels are built at Blender build time, one `kernel.cu` translation unit per architecture, to cubin (or PTX for `compute_*`), with `--use_fast_math`, `-std=c++17`, and `--jump-table-density 80` for sm_120+ on CUDA 12.3+. `--split-compile=0` is used only when there are two or fewer binaries, "to avoid excessive memory usage". The architecture list is a CMake variable (`CYCLES_CUDA_BINARIES_ARCH`). VERIFIED https://raw.githubusercontent.com/blender/blender/main/intern/cycles/kernel/device/cuda/CMakeLists.txt
- OptiX: kernels are compiled with `--ptx` (not OptiX-IR) and zstd-compressed. `kernel.cu` contains only five raygen entry points that call the shared `integrator_intersect_*` functions; no closest-hit/any-hit programs and no `optixReorder` in that file. Shading stays in the CUDA wavefront kernels. VERIFIED https://raw.githubusercontent.com/blender/blender/main/intern/cycles/kernel/device/optix/CMakeLists.txt and https://raw.githubusercontent.com/blender/blender/main/intern/cycles/kernel/device/optix/kernel.cu
- The slowest kernel is split out and loaded lazily: `kernel_shader_raytrace.cu` is "a copy of the regular kernels with additional shader ray-tracing kernel that takes much longer to compile. This is only loaded when needed by the scene." VERIFIED https://raw.githubusercontent.com/blender/blender/main/intern/cycles/kernel/device/optix/kernel_shader_raytrace.cu
- CPU: Embree for ray traversal, runtime-selected SSE/AVX2 kernel variants compiled from the same source. VERIFIED (BVH doc) https://developer.blender.org/docs/features/cycles/bvh/ ; REPORTED (variants) https://raw.githubusercontent.com/blender/blender/main/intern/cycles/kernel/device/cpu/kernel.cpp
- History: Cycles X (3.0) moved from one large kernel to a wavefront/microkernel design: higher occupancy, sorting, reduced compile time, lower register pressure, "despite that, still large kernels". The shader VM is a stack machine (`float[255]`, 98-node switch) and is called out as a high-register, long-compile-time kernel. An OpenCL split-kernel port was removed in 3.0 because of "discrepancies between OpenCL and CUDA code" and driver bugs. VERIFIED (Intel/Blender slides) https://www.iwocl.org/wp-content/uploads/iwocl-2025-xavier-hallade-write-once-deploy-many.pdf

pbrt-v4:
- `PBRT_CPU_GPU` is `__host__ __device__` when `__CUDACC__` and the GPU renderer are on, otherwise empty. VERIFIED https://raw.githubusercontent.com/mmp/pbrt-v4/master/src/pbrt/pbrt.h
- The book says almost all of pbrt runs on both CPU and GPU, polymorphism is tag-based dispatch (a unique integer per type) instead of virtual functions, and integrators of the CPU path are CPU-only. VERIFIED https://pbr-book.org/4ed/Introduction/pbrt_System_Overview
- The wavefront integrator is one code body that runs on CPU (`--wavefront`) or GPU; `ParallelFor` routes by a GPU option; the CPU wavefront path is for debugging and testing and is usually slower than the CPU volumetric path tracer. REPORTED (search snippet of the book) https://pbr-book.org/4ed/Wavefront_Rendering_on_GPUs/Path_Tracer_Implementation.html ; selection code VERIFIED https://raw.githubusercontent.com/mmp/pbrt-v4/master/src/pbrt/wavefront/wavefront.cpp
- OptiX only traverses: four raygen, six closest-hit, three miss, four any-hit, two intersection programs; they build the interaction and enqueue work, and material evaluation is in separate CUDA kernels. OptiX does not link with the main CUDA code, so a few `.cpp` files are `#include`d into `optix.cu`. VERIFIED https://raw.githubusercontent.com/mmp/pbrt-v4/master/src/pbrt/gpu/optix/optix.cu
- Build: PTX via CMake CUDA_PTX_COMPILATION, `--use_fast_math --extended-lambda`, global `-maxrregcount 128` outside debug, no launch bounds, block size from the occupancy API at run time. VERIFIED https://raw.githubusercontent.com/mmp/pbrt-v4/master/CMakeLists.txt and https://raw.githubusercontent.com/mmp/pbrt-v4/master/src/pbrt/gpu/util.h
- The book's stated reasons for wavefront over megakernel: divergence, register allocation "must be made according to the worst case", and long compile times of a large kernel. VERIFIED https://pbr-book.org/4ed/Wavefront_Rendering_on_GPUs/Mapping_Path_Tracing_to_the_GPU

Reading: both shipped renderers keep traversal as the one backend-specific part, run shading in plain CUDA kernels, and cap registers explicitly (168 via launch bounds, 128 via global flag). Neither relies on a new language.

### F2. Register saturation and build time are properties of the NVIDIA backend compiler, not the front-end language

- NVRTC, nvcc, OptiX module creation and Dr.Jit's PTX all end in the same NVVM + ptxas path; Slang's CUDA/OptiX target emits CUDA C++ and uses NVRTC (it requires NVRTC to find `optix.h`; v2026.18.2 added NVRTC precompiled headers for its CUDA prelude). VERIFIED https://raw.githubusercontent.com/shader-slang/slang/master/docs/cuda-target.md and https://github.com/shader-slang/slang/releases . Inference: switching language does not change the register allocator or ptxas time for the CUDA/OptiX route. UNVERIFIED that the Vulkan/SPIR-V route differs; the NVIDIA driver compiler is a separate code path I did not measure.
- NVIDIA's own compile-time guide lists the levers, all language-independent. Caveat (verified): `--Ofast-compile` is off by default and costs "modest to significant" run time, `--register-usage-level` (ptxas, default 5) can cost "potentially significant" run time, so both are dev/test-only levers, not release levers; only `--split-compile` and `-pch` list no or minimal run-time impact. Slang can also emit CUDA source for nvcc or drive NVRTC itself (`-target ptx`), so "NVRTC" is one of two CUDA routes, both ending in ptxas: `--threads` (multi-arch only), `--split-compile N` (per-function parallel optimisation, "minimal" runtime impact), `--Ofast-compile`, ptxas `--opt-level`, `--register-usage-level 0..10`, `-time`, `-fdevice-time-trace`, NVRTC `-pch`, avoiding `__forceinline__` code explosion, marking big rarely-hot functions `__noinline__`, limiting unrolling. NVRTC PCH "serializes frontend processing". VERIFIED https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/compile-time.html
- OptiX module options expose `maxRegisterCount` ("may vary within a pipeline"), `optLevel`, `boundValues` (specialisation constants) and `baseModule`. VERIFIED https://raytracing-docs.nvidia.com/optix9/api/struct_optix_module_compile_options.html . OptiX 9.1 added module-creation cancellation, an application-side compile-cache API and "pipeline options for faster builds". REPORTED (forum announcement text only) https://forums.developer.nvidia.com/t/optix-9-1-release/354119 . Effect sizes: UNVERIFIED.
- The guide has "15.3 Non-inlined functions" and "15 Callables" sections; NVIDIA's reply on continuation callables says they remain the only way to do recursive trace in a callable and that the callable rules were changing with SER. `optixTrace` from direct callables is unsupported since 9.0. VERIFIED (ToC) https://raytracing-docs.nvidia.com/optix9/guide/index.html ; VERIFIED https://forums.developer.nvidia.com/t/are-continuation-callables-actually-necessary/232473 and https://forums.developer.nvidia.com/t/optix-9-0-release/322842 . Whether callables isolate register pressure per material: UNVERIFIED, must be measured.
- v1 evidence (recon): ~95-register base plus two ~160-register consumers (NEE block, spectral BSDF union) in one fused shade kernel; 128 template variants in one TU cost ~1,800 s, cut to ~8 min by splitting into 12 TUs.

### F3. Slang (state at v2026.22, 2026-11-10)

Maturity by target:
- Releases are monthly or faster (v2026.17 on 4 Sep through v2026.22 on 10 Nov) with breaking-change lists in most of them (v2026.20 SPIR-V debug scopes, v2026.21 CUDA GatherCmp rejected, v2026.22 CUDA Gather offsets now a capability error, serialized-module compatibility now enforced from v2026.18.2). VERIFIED https://github.com/shader-slang/slang/releases
- CUDA/OptiX is actively developed: callable shaders added in v2026.17, `GeometryIndex()` on CUDA/OptiX in v2026.20, SER `HitObject::Invoke` lowering on CUDA in v2026.18, an OptiX payload fix for bool/half types in v2026.1.2, a CUDA compile-time cubic-scaling regression fixed in v2026.18.2. VERIFIED (releases page above) ; REPORTED (2026.1.2) https://newreleases.io/project/github/shader-slang/slang/release/v2026.1.2
- CORRECTED: `cuda-target.md` does not call OptiX a work in progress (it says "Slang supports OptiX for raytracing"; the "work in progress" wording there refers to texture resource types, and the target is described as "preliminary support" for CUDA source and PTX via NVRTC). Docs list no CUDA feature matrix; the CUDA doc covers texture/sampler/wave limitations and OptiX 7.1/8.1/9.0 behaviours (OptiX 9.0+ `MakeHit` ignores hit-identifying arguments). Docs may lag releases. VERIFIED https://raw.githubusercontent.com/shader-slang/slang/master/docs/user-guide/09-targets.md and https://raw.githubusercontent.com/shader-slang/slang/master/docs/cuda-target.md
- SER: D3D12 (NVAPI or DXR 1.3), Vulkan (NV or EXT extension), CUDA via `optixTraverse/optixInvoke`; needs OptiX 8.0/8.1. VERIFIED https://shader-slang.org/slang/shader-execution-reordering.html
- Pointers with address space are "available in Metal & CUDA", Vulkan "not considered stable"; an "optional experimental LLVM backend" is listed as available; "portable ray tracing" is in design, with an experimental API added in v2026.22. VERIFIED (vendor slides, footer dates inconsistent) https://www.khronos.org/developers/linkto/slang-in-action-slides and releases page.
- CPU target, the weak spot. The C++ target: no user atomics (`InterlockedAdd` fails with E36107), no `groupshared`, no barriers, no ray queries (`TraceRayInline` on cpp/LLVM is E36107; an issue opened 2026-10-16 is still open with no maintainer decision on 2026-11-06). VERIFIED https://github.com/shader-slang/slang/issues/13705 and https://raw.githubusercontent.com/shader-slang/slang/master/docs/cpu-target.md . The direct LLVM target is "highly experimental": threads in a group run serially, no acceleration structures/textures, vectorisation weaker than GPU lanes; recent open issues include an internal error on a global `RWStructuredBuffer` (#14329, 2026-11-04) and a crash/hang on concurrent first compile (#14443). VERIFIED https://raw.githubusercontent.com/shader-slang/slang/master/docs/llvm-target.md ; REPORTED (issue titles via search) https://github.com/shader-slang/slang/issues/14329
- Compile speed evidence is front-end/SPIR-V only. NVIDIA's talk on porting nvpro samples: a 161,720-byte path tracer split into 16 modules plus a main file, optimisations and validation off, in memory; module caching improved hot-reload compile time by 39%; the chart axis tops out at 1,400 ms (bar values not extractable from the PDF). For vk_gaussian_splatting, 673 ms with `#include`, 597 ms with one module per file, 744 ms with one module total. This is Slang to SPIR-V; it excludes the driver's SPIR-V to SASS compile and says nothing about the CUDA/NVRTC route. VERIFIED https://www.khronos.org/developers/linkto/upgrading-from-glsl-to-slang-in-the-vulkan-nvpro-samples
- Language features relevant to a renderer: generics/interfaces/modules; link-time specialisation that reuses front-end work (no measured numbers in the doc); interface-typed values specialise when the concrete type is known, otherwise "dynamic dispatch ... may introduce performance overhead". VERIFIED https://raw.githubusercontent.com/shader-slang/slang/master/docs/user-guide/10-link-time-specialization.md and https://raw.githubusercontent.com/shader-slang/slang/master/docs/user-guide/06-interfaces-generics.md
- Ray-tracing shaders in a path tracer in Slang: the nvpro vk_gltf_renderer is generic over an `IRaytracer` interface with ray-query and RT-pipeline implementations, and uses `HitObject::TraceRay` + `ReorderThread`. VERIFIED (same slides as above).
- Who uses it: Falcor 2's path tracer (MaterialX added a Slang generator), Autodesk Aurora and NVIDIA Omniverse per vendor slides. All real-time. I found no offline production renderer built on Slang. VERIFIED (slides) https://www.khronos.org/developers/linkto/slang-in-action-slides ; MaterialX generator VERIFIED https://www.aswf.io/blog/materialx-adds-support-for-slang-shader-generation/ (no version or targets stated). The only Blender-adjacent engine found, "Spectra Render", uses Rust + Vulkan RT + Slang in an out-of-process daemon; alpha, closed, claims unverified, no timings besides one 1000x1000 render under 8 s on a laptop RTX 3080. REPORTED https://blenderartists.org/t/spectra-realtime-restir-caustics-true-spectral-engine-for-blender-rust-vulkan-addon/1655156
- NVIDIA's RTX Path Tracing SDK is HLSL, DX12 first, "SER and OMM support on Vulkan is currently work in progress"; it does not use Slang or CUDA. VERIFIED https://github.com/NVIDIA-RTX/RTXPT
- No Slang-vs-handwritten-CUDA benchmark found. UNVERIFIED performance parity. NVIDIA's Slang slides claim runtime performance "can meet or beat" hand-written code (vendor claim, SIGGRAPH 2026 lab slides, VERIFIED as a claim) https://developer.download.nvidia.com/ProGraphics/nvpro-samples/SlangLab/Slides-2026.pdf

### F4. Vulkan ray tracing and the cross-vendor question

- Vulkan SER became `VK_EXT_ray_tracing_invocation_reorder` (ratified, revision dated 2025-11-12, NVIDIA and AMD contributors); reordering is a hint (`rayTracingInvocationReorderReorderingHint`); NVIDIA cites up to 47% in the glTF path tracer. VERIFIED https://docs.vulkan.org/refpages/latest/refpages/source/VK_EXT_ray_tracing_invocation_reorder.html , https://docs.vulkan.org/features/latest/features/proposals/VK_EXT_ray_tracing_invocation_reorder.html , https://vulkan.org/news/auto-24031-ae7c3606d9a0ffa93844013e31d5d8fa . Which NVIDIA driver exposes the EXT version: UNVERIFIED.
- Curves: Vulkan only has built-in triangles plus an NVIDIA-only, unratified linear-swept-sphere extension (revision 1, 2025-01-03). OptiX has native curves; 9.0 added hardware LSS on Blackwell, Rocaps software curves, clusters (RTX Mega Geometry) and cooperative vectors. VERIFIED https://docs.vulkan.org/refpages/latest/refpages/source/VK_NV_ray_tracing_linear_swept_spheres.html and https://forums.developer.nvidia.com/t/optix-9-0-release/322842 ; the older forum answer on OptiX vs Vulkan features is REPORTED and dated https://forums.developer.nvidia.com/t/what-are-the-advantages-and-differences-between-optix-7-and-vulkan-raytracing-api/220360
- Performance: no controlled OptiX-vs-Vulkan study found. One user report (untextured Sponza path tracer): 8.0 ms OptiX, 2.7 ms DXR, 1.7 ms Vulkan, attributed by the reporter to kernel compilation and an acceleration-structure mode; a forum reply says to use two-level instancing. REPORTED, not controlled https://forums.developer.nvidia.com/t/ray-tracing-performance-in-optix-vs-vulkan-dxr/260558
- RT pipelines can contain thousands of shaders and pipeline creation can stall; pipeline libraries (`VK_KHR_pipeline_library`) allow incremental compilation. No seconds measured. REPORTED https://docs.vulkan.org/guide/latest/extensions/ray_tracing.html
- Blender's own choice: Cycles uses a different vendor RT library per device (Embree on CPU/Intel, OptiX on NVIDIA, HIPRT on AMD, MetalRT on macOS; its custom BVH is a fallback to be removed). VERIFIED https://developer.blender.org/docs/features/cycles/bvh/ . Blender 5.1 enabled HIP-RT by default on AMD (REPORTED https://phoronix.com/news/blender-5.1-released); HIPRT 3.2 released 2026-10-21 (REPORTED https://phoronix.com/news/AMD-HIPRT-3.2). Blender's docs say Vulkan is for the UI, not planned as a Cycles compute backend (recon; VERIFIED there https://developer.blender.org/docs/features/gpu/vulkan/).
- Blender's `DisplayDriver` interop (Vulkan buffer handles, CUDA import) is a C++ interface for engines built into Blender; a Python add-on cannot implement it, and recon found no Python API to import external GPU memory into a `GPUTexture`. Cycles 5.3 notes have no interop item. VERIFIED https://developer.blender.org/docs/release_notes/5.3/cycles/ ; interop negative result carried from recon (00-recon.md, engine-integration). Inference: for an add-on engine, a Vulkan renderer gains no zero-copy advantage over CUDA/OptiX; both stage through host memory. Verified 2026-11-14: Python `gpu.types.GPUTexture(size, layers, is_cubemap, format, data)` accepts only a `gpu.types.Buffer`; `GPUStorageBuf` likewise; neither has external-handle import. Residual caveat (UNVERIFIED, S5): a native extension module could in principle share Blender's OpenGL context and use CUDA-GL interop; Blender's docs say Vulkan is for the UI and not used for Cycles, and say nothing on interop.
- GPU market: NVIDIA ~90% of desktop GPU shipments in Q1 2026 (JPR, REPORTED, whole market not Blender users) https://tweaktown.com/news/112161/desktop-gpu-shipments-hold-steady-in-q1-2026-with-nvidia-maintaining-90-percent-market-share/index.html . Blender Open Data vendor split could not be read from the page. UNVERIFIED.

One user, unreproduced publicly. VERIFIED (post read) https://forums.developer.nvidia.com/t/optix-9-1-ser-optix-ir-crashes-with-hags-enabled-cuda-719-ptx-appears-stable/387608 . - nvcc on Windows: the CUDA 13.5 install guide lists MSVC (VS 2026, 2022, 2019) as the supported host compilers and does not mention clang/clang-cl. VERIFIED https://docs.nvidia.com/cuda/cuda-installation-guide-microsoft-windows/index.html

### F6. Dr.Jit (tracing JIT)

- Releases: 1.3.0 (2026-02-16, Blackwell sm_120 wide loads/atomics), 1.4.0 (2026-06-25, Metal backend; CUDA backend now needs compute capability 7.5+ and R535+; tracing and bindings overhead roughly halved; freeze replay up to ~2.5x faster), 1.5.0 (2026-08-07, LRU on-disk kernel cache), 1.6.0 unreleased (kernels split into many compilation units compiled and cached in parallel; LLVM via ORCv2/JITLink with cached objects and LLVM 18+; GDB/LLDB debugging of LLVM kernels on Linux and macOS only; OptiX custom intersections). VERIFIED https://drjit.readthedocs.io/en/latest/changelog.html
- SER via `dr.reorder_threads()` since 1.1.0, OptiX 8.0 ABI required. REPORTED (search snippet of changelog) https://drjit.readthedocs.io/en/v1.1.0/changelog.html
- Control flow: symbolic mode (default) traces loops into one kernel, "tends to create much larger kernels", may use many registers and diverge; evaluated mode runs each iteration as separate kernels with memory-bandwidth cost "prohibitive" in the docs' words. This is exactly the megakernel-vs-wavefront trade-off v1 hit. VERIFIED https://drjit.readthedocs.io/en/latest/cflow.html
- `@dr.freeze` replays recorded kernels to remove tracing cost; GPU acceleration-structure builds and custom CUDA launches must be outside the frozen function; no numbers in the doc. VERIFIED https://drjit.readthedocs.io/en/latest/freeze.html
- Platform: LLVM backend needs LLVM 18+ installed (Windows: official installer); Python 3.10+ in 1.6. VERIFIED https://drjit.readthedocs.io/en/latest/what.html
- Mitsuba 3.9.1 (2026-08-07) is "an experimental research framework", not SemVer; build time and memory scale with the number of variants (more than five "may not be advisable"); needs VS 2022 on Windows. VERIFIED https://mitsuba.readthedocs.io/en/latest/release_notes.html and https://mitsuba.readthedocs.io/en/latest/src/developer_guide/compiling.html
- No public offline production renderer on Dr.Jit found. UNVERIFIED that built-in OptiX curves or clusters are exposed.

### F7. Other options

- SYCL / DPC++: Cycles' oneAPI backend run on an RTX 3080 (Windows 24H2, driver 560.94, CUDA 12.8, `-Xcuda-ptxas --maxrregcount=128`, device globals) reached 96-100% of the CUDA backend on the benchmark scenes shown; the baseline is the CUDA path, not OptiX. The same Intel/Blender deck says hardware RT is vendor-specific (HIP RT, OptiX) "not compatible with SYCL" and Vulkan RT "cannot be efficiently mixed with SYCL"; Embree-on-SYCL is Intel GPUs only. VERIFIED (vendor deck) https://www.iwocl.org/wp-content/uploads/iwocl-2025-xavier-hallade-write-once-deploy-many.pdf . I found no SYCL RT extension or NVIDIA RT-core access from SYCL. UNVERIFIED beyond that.
- HIPRT: AMD-only RT library; relevant only for an AMD port. REPORTED (above).
- ISPC: CPU SPMD compiler, v1.32 about 2026-10-14 (REPORTED https://phoronix.com/news/Intel-ISPC-1.32-Released); GPU targets are Intel Xe only, so it is a second language for CPU, not single-source.
- Rust: wgpu supports ray queries behind an experimental flag; RT pipelines are in development (PR opened 2026-04-25); no SER. REPORTED https://wgpu.rs/doc/src/wgpu/documentation/extensions/ray_tracing.rs.html . NVIDIA cuda-oxide (Rust to CUDA) 0.1 in May 2026, 0.2 in June, experimental, Windows lagging. REPORTED https://phoronix.com/news/nvidia-cuda-oxide-0.1 . Rust-GPU targets SPIR-V; no ray-tracing evidence. Host language and kernel language are separate choices; Spectra uses Slang for shaders.
- LuisaCompute/LuisaRender (C++ embedded DSL, CUDA/DX/Metal/CPU backends, SIGGRAPH Asia 2022): 2026 status unverified. NVIDIA Warp (Python JIT via NVRTC, CPU and CUDA): ray queries use its own BVH, no RT-core evidence found. REPORTED https://nvidia.github.io/warp/v1.17/project/changelog.html
- MaterialX/OpenPBR: MaterialX has a Slang generator (above); Blender's OSD 2026 slide names OpenPBR v1.1.1. REPORTED via recon (not re-read).

## Options and tradeoffs

Axes that actually separate the options:

| Axis | C++ + thin layer (a) | Slang (b) | Vulkan RT + Slang/GLSL (c) | Dr.Jit (d) |
|---|---|---|---|---|
| CPU target quality | Best: native C++, MSVC/clang-cl, full debugger, sanitizers | Weak today: C++ emit lacks atomics/ray queries; LLVM "highly experimental" with open ICEs | Needs separate CPU path (Slang CPU or C++) | Good throughput (LLVM, AVX512), Windows needs LLVM install; debugger support Linux/macOS only |
| NVIDIA peak | Full OptiX 9.x (SER, LSS, clusters, coop-vec), PTX or IR | OptiX/CUDA via NVRTC; curves/clusters via escape hatch unverified; parity unmeasured | Vulkan RT; curves NV-only extension; SER EXT driver status unknown | OptiX through Dr.Jit API only; megakernel by default |

Real forks (not manufactured options):

1. CPU as correctness oracle only, or as a shipping device? If only an oracle at tiny resolution, Slang's C++ target becomes viable for shading code, but traversal must still be a backend service (no ray queries on CPU). If the CPU must be a competent render device, native C++ (or Dr.Jit LLVM) is the safe side.
2. Where the compile cost lands: at project build (nvcc, deterministic, ships binaries), or at first run (NVRTC/Dr.Jit/Slang, cached, needs redistributable compiler and a cache story). These are not exclusive: the same C++ source can feed both.
3. Specialise per material at compile time (more kernels, fewer registers each, template matrix risk) or dispatch at run time (fewer kernels, uniform worst-case registers). pbrt uses tag dispatch inside per-class kernels; v1's 128-variant template matrix is the failure case.
4. Language-level conveniences (generics, modules, autodiff) versus the fewest moving parts between source and ptxas.
5. Hardware-feature access per language: curves, clusters, SER, cooperative vectors are host/device API features that C++ gets on day one and others get through wrappers.

What structurally avoids v1's saturation and 30-minute builds (all language-independent unless noted):
- Per-stage wavefront kernels with bounded state (Cycles, pbrt): the register ceiling becomes max over stages instead of a union of all lobes plus NEE. Directly addresses v1's cause; whether OpenPBR's layers fit under the cap is the spike.
- Explicit register budget per kernel via `__launch_bounds__` (Cycles 168 at 384 threads) or OptiX `maxRegisterCount`, accepting small spills in cold stages; never relying on the compiler's default.
- Heavy, rarely used kernels isolated and loaded on demand (Cycles' `kernel_shader_raytrace`).
- Single-architecture dev builds (sm_120), `--Ofast-compile`/lower ptxas levels for tests, `--split-compile` for release, one stage per TU so one edit rebuilds one kernel.
- No template variant matrix; runtime tag dispatch or specialisation constants (OptiX `boundValues`, effect unverified).
- JIT/runtime compile (NVRTC, Dr.Jit) removes compile from the project build and enables hot reload, but ptxas time per kernel is unchanged; it only helps if kernels are small and cached.
- Evaluated-mode (wavefront) rather than symbolic loops if Dr.Jit were used.

NVIDIA-only versus vendor-neutral, as a real trade: vendor-neutral costs a second traversal backend and second feature matrix, testing on hardware the owner does not have (RTX 5070 Ti only), and loses curves/clusters/OptiX denoiser integration unless gated per vendor. It buys nothing for the Blender-addon viewport (no interop advantage, F4) and the one shipped Blender renderer chose per-vendor RT.

## Recommendation for Astroray 2.0

1. Kernel language: plain C++ in a restricted subset, header-only kernel library with a thin portability layer (function qualifiers, address spaces, thread indexing, atomics, ballot), in the Cycles/pbrt style. Compile for CPU with the host compiler (MSVC, which nvcc requires anyway; clang-cl optional), and for GPU with NVRTC for dev/hot reload and nvcc for release/CI, from the same source. Evidence: F1 (two shipping renderers, one macro layer ported by Cycles to CUDA, OptiX, HIP, HIPRT, Metal, oneAPI), F2 (the register allocator and ptxas are shared by every NVIDIA route, so a new language does not remove the problem), F3 (Slang CPU/LLVM and C++ targets lack atomics and ray queries and carry open internal errors; monthly breaking releases), F5 (OptiX 9.x features are native in C++).
2. Structure, not language, fixes v1's problem: wavefront with small per-stage kernels, bounded closure/lobe state sized by the OpenPBR layer model, NEE and shadow rays in their own stages, explicit launch bounds (start from Cycles' 384 threads/168 registers on sm_120 and measure), one stage per TU, lazily loaded heavy kernels, no template variant matrix. Set the build budget as: dev build single-arch (`sm_120`) with `--Ofast-compile`, release builds multi-arch with `--split-compile`, `-time` and `-fdevice-time-trace` tracked in CI. Whether the 30 s incremental and 5 min clean budgets hold for GPU code is unproven (see spikes).
3. Traversal is a backend service behind one interface (closest hit, any hit) and the only intentionally backend-specific code: OptiX on GPU (PTX by default, OptiX-IR behind a switch until the HAGS/SER crash is understood), Embree on CPU. Shading never lives in OptiX hit programs (pbrt and Cycles both enqueue and shade in CUDA kernels), which also leaves explicit material sorting as the coherence mechanism; SER stays an optional experiment (inference: with per-material queues SER matters less; unmeasured).
4. GPU backend: NVIDIA-first (CUDA + OptiX), not NVIDIA-only by design. Keep the portability layer and the traversal interface clean so an AMD (HIP + HIPRT) or other port is a new backend, as in Cycles, but promise, build and test none of it in 2.0. Reasons: owner hardware and priority on viewport speed; NVIDIA-only features (OptiX curves/LSS, clusters, cooperative vectors, denoiser) have no ratified cross-vendor equivalent; Vulkan RT gives no Blender-interop gain for an add-on (F4); Blender itself uses per-vendor RT libraries; CLAUDE.md rule 7 (fail loudly) argues against shipping untested vendor paths.
5. Slang is a time-boxed spike, not the baseline. Revisit if the spike meets the criteria below; the main attraction is MaterialX/OpenPBR codegen and module-level compile modularity, the main blocker is the CPU oracle. Dr.Jit is not recommended: its default symbolic mode reproduces the megakernel problem, it is a research framework with weak Windows debugging, and it constrains OptiX feature access. SYCL, ISPC, Rust kernels, Warp and LuisaCompute are not recommended (F7).
6. Treat NVRTC redistribution (licence) and CPU wavefront throughput as owner-visible risks until the spikes close.

## What a measurement spike must settle

All on the RTX 5070 Ti, sm_120, with the commands recorded. Keep each spike under two days; do not build engine code.

S1. Register and compile budget (decides the baseline).
- Write one wavefront shade stage in C++: OpenPBR subset (base diffuse, specular GGX, metal, coat, transmission) with 4 hero wavelengths and a fixed-size lobe struct, plus a separate NEE stage and a separate bounce-sample stage.
- Report `-Xptxas -v` registers/spills (or `cuobjdump --dump-resource-usage`) per stage, with and without `__launch_bounds__(384, 168)`; compile wall time cold and warm for: nvcc default, `--split-compile`, `--Ofast-compile`, `-Xptxas --register-usage-level`, NVRTC with/without `-pch`. Pass: every stage below 168 registers with no spills in hot stages, one-stage edit rebuild under 30 s. Fail means the bounded-state design needs rework before language matters.

S2. Slang parity (decides whether Slang stays a candidate).
- Port the S1 stages to Slang. Compare: Slang to CUDA via NVRTC (registers, compile time, kernel time within 5% of S1?), Slang to SPIR-V as Vulkan compute with `rayQueryEXT` (driver compile time, kernel time), Slang CPU via C++ emission and via LLVM (does it compile, are atomics/ray queries needed, results within ULP tolerance of the C++ CPU build, ICEs). Record Slang version pinned and any breaking-change churn over the spike. Criteria to switch baseline: CPU target compiles the full shade stages without escape hatches, CUDA-route performance and registers within 5% of C++, and OptiX curves/LSS reachable.

S3. CPU path viability.
- Run the same wavefront stages on CPU (pbrt-style `ParallelFor`) versus a per-path loop at 64x64 and 256x256; measure time per furnace test and the pre-commit budget (under 10 s). Decide if the CPU is oracle-only or a device (owner question below).

S4. OptiX specifics.
- PTX vs OptiX-IR: kernel time and module-creation time, and a repro attempt of the SER + HAGS crash on the 5070 Ti with driver version recorded. SER on/off with and without explicit material sort. Module creation time with the 9.1 compile cache. Per-module `maxRegisterCount` and `boundValues` effect on registers/compile time. Optional: callable vs inlined material eval register impact.

S5. Viewport path.
- Time GPU result to Blender `GPUTexture` at 1080p RGBA16F for CUDA to pinned host to `gpu.types.Buffer`; confirm whether Blender 5.3's Python `gpu` API offers any external-memory import (including the new `GPUStorageBuf`); test Vulkan and OpenGL backends. This closes the interop claim in F4.

S6. Hot reload.
- Edit one BSDF constant; measure edit-to-pixels for NVRTC + OptiX module re-create, and for the CPU DLL reload, against the viewport budget.

S7. Dr.Jit sanity (only if S1 fails). One BSDF furnace in evaluated vs symbolic mode: kernel size, registers, compile time, embedding in Blender's Python 3.13, LLVM on Windows.

S8. Licence check. Read the current CUDA EULA Attachment A for NVRTC/nvJitLink redistribution and the OptiX SDK licence for shipping PTX/modules in a Blender extension.
