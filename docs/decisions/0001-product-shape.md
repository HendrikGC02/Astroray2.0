# 0001 — Product shape, platforms, language, licence and distribution

Status: proposed (2026-11-14), revised after independent review (same day), reconciled with `RULINGS.md` (same day)

## Context

Astroray 2.0 is a spectral path tracer for physically accurate and astrophysical rendering, used mainly from Blender. This record fixes what gets built and shipped, where it runs, what it is written in, under which licences, how users get it, which third-party code it may use, how the engine fails and reports, and what 2.0 leaves out. Records 0002-0009 build on it. Under `RULINGS.md` this record owns the C ABI rules, naming, versioning, the error and status model, and the per-render report.

Binding inputs:
- Owner decisions (`0000-owner-decisions.md`): one kernel source for CPU and GPU (2); ship on Blender 5.3, design for 5.4 (3); language is the lead's call (4); engine core Apache-2.0, addon GPL-3.0-or-later, fully open source, no commercial option (5); public repository (6); the first release has the full feature breadth (7); a Cycles-class viewport (9, 10); DLSS if possible (11); addon only, no Blender fork (14). Lead defaults: self-hosted distribution, Windows only, a CPU target that is for correctness and can also render, unsupported nodes magenta and listed in a per-render report.
- Spine §1: a C++ core behind a small versioned C ABI (`astroray_core.dll`), a thin GPL Python extension loading it with ctypes, a command-line host, NVIDIA first (CUDA + OptiX, Embree on CPU), and no NVIDIA binaries or headers in the repository.
- Evidence: spike A (kernel compile and register budget, CPU/GPU agreement) and spike B (Blender in-process ctypes DLL, sync and present costs), both on this machine (RTX 5070 Ti, CUDA 12.8, MSVC 19.44, OptiX 9.1, Blender 5.3.0 on Vulkan). Inspected for this revision (file versions and `dumpbin /dependents`, Blender 5.3.0 install, 2026-11-14): `blender.crt\vcruntime140.dll` is 14.44.35211; `blender.shared\` holds OIDN 2.5.0 (`OpenImageDenoise.dll`, `_core`, `_device_cpu`, `_device_cuda`, `_device_hip`, `_device_sycl`) and oneTBB 2022.3.0 (`tbb12.dll`, `tbbmalloc*.dll`); `OpenImageDenoise_device_cpu.dll` imports `tbb12.dll`, and all OIDN modules import `MSVCP140`/`VCRUNTIME140`.
- Owner priorities that bear on this record: short builds, fast tests, simplicity, and development by Sonnet-class agents from small specs. These favour one language, one artifact, mechanical interfaces and checks run by scripts.

## Decision

### D1. Deliverables

1. **Engine library** `astroray_core.dll` (Apache-2.0), the only Astroray binary Blender loads. It contains the host code, the CPU device (the kernel source built by MSVC, plus Embree), the CUDA device (CUDA kernels, OptiX traversal), and, in release builds, the kernels and generated data tables embedded as Win32 `RCDATA` resources (ruling 13). It does not depend on Blender or Python. Apart from optional data packs (D8.5) and the OIDN DLLs (D9), a release needs nothing beside this file. Embedding rules out a mismatch between the DLL and loose kernel files (v1 stale-artifact lesson, `v1-lessons/toolchain-and-build.md`). Only development builds load kernel modules as loose files from the build tree.
2. **C ABI** `include/astroray/astroray.h`: the only public header, in C (C11-compatible), written in the restricted grammar of D2.10.
3. **Blender extension** `astroray` (GPL-3.0-or-later): pure Python, using only Blender's bundled Python 3.13, `ctypes` and NumPy. It ships no wheels and no `.pyd`. It contains the `RenderEngine`, the UI, depsgraph diffing and the ctypes binding `astroray/_abi.py`, which is **generated** from `astroray.h` into the build tree, staged into the zip, never committed and never edited. `_abi.py` carries an Apache-2.0 SPDX line (Apache-2.0 files may sit inside a GPLv3 work) because Apache tests and tools import it. 0007 owns the extension's structure.
4. **Command-line host** `astroray_cli.exe` (Apache-2.0). It uses only the public C ABI, so tests and benchmarks exercise the same path as Blender. Subcommands (ruling 38): `info` (devices, driver, ABI hash, build info), `render <recording> -o <path>`, `bench <recording>`, `dump` (scene-state and film dumps, 0009 decision 17a, 0008 decision 13); 0009 owns flag spellings. **The CLI and the test executables are the primary development host for engine work**; Blender is used for integration checks (0009 17a). A GPU fault during development then costs a process restart, not a Blender session (D2.5).

   **Scene input is an ABI recording** (`.arrec`). The recorder stores the *input* calls only (D2.10) with their array payloads; the CLI replays them. The recording header carries the ABI hash and `ar_build_info()`, and replay refuses a hash mismatch. Scenes reach the CLI by (a) recording a Blender sync or (b) running a Python builder that calls the ABI through `_abi.py`. Recorder and replayer are generated by the same generator as `_abi.py`. There is no second scene format in 2.0.

### D2. C ABI conventions, versioning and reporting

1. **Naming.** Functions are `ar_<object>_<verb>`, types `ar_<name>`, constants `AR_<NAME>`. Objects are opaque handles: `ar_context` (device discovery, logging, recording; a context is created for one device, CPU or CUDA with an index, selected in `ar_context_desc` with the log path of D2.5 and the recording path of D1.4; ruling 33), `ar_scene`, `ar_session` (one render: viewport, final or preview, owning its film and its report), and `ar_edit` (one open scene-edit transaction on an `ar_scene`, 0007 decision 5; ruling 33). Several contexts, scenes and sessions coexist in one process: viewport, F12 and material previews run at once (research 01 B5). The engine holds no process-global mutable state (CLAUDE.md rule 8). The one shared thing it cannot avoid is CUDA's primary context: static cudart gives every `ar_context` the same context per device, so a GPU fault is process-wide (D2.5).
   **Context and device functions** (ruling 33; fields as named, widths fixed in `astroray.h` under D2.2): `ar_context_desc` {device_kind u32 (`AR_DEVICE_CPU`, `AR_DEVICE_CUDA`), device_index u32, log_path (`AR_IN` string, D2.5), record_path (`AR_IN` string, NULL = no recording, D1.4)}; `ar_device_info` {kind u32, index u32, status u32 (the `ar_status` context creation would return, D2.8), compute capability u32, memory bytes u64, name u8[64], reason u8[128]}. `AR_QUERY ar_device_count(AR_OUT uint32_t* count)` and `AR_QUERY ar_device_get_info(uint32_t index, AR_OUT ar_device_info*)` need no context and serve the CLI's `info` and the addon's device list; `ar_context_create(AR_IN const ar_context_desc*, AR_OUT ar_context*)`; `ar_context_destroy(ar_context)`, after every scene on it is destroyed.
2. **Types.** Structs are POD with fixed-width fields only (`uint32_t`, `int32_t`, `uint64_t`, `float`, `double`, annotated pointers, and `uint8_t` only as fixed arrays of NUL-terminated UTF-8 text). Padding is explicit and alignment natural. No bitfields, no `bool`, no enum types (enum values are `#define` constants stored in `uint32_t`). The one allowed scalar typedef is `typedef uint64_t ar_key;`, the host-assigned datablock key (0007 decision 18; ruling 33). Strings are UTF-8.
3. **Bulk data.** Arrays are passed with an explicit element type and count, in two forms only:
   - Copy-in (`AR_IN_ARRAY`): the engine reads the caller's array during the call; the caller may free it on return.
   - Staging (`AR_STAGED`): `..._begin` returns engine-owned writable pointers, the caller fills them (for example `foreach_get` straight into native memory; research 01 D2, spike B §2.1), and `..._commit` hands them back.
   Engine memory is freed only by the engine. A returned pointer stays valid until the invalidating call named in its header comment.
4. **No callbacks across the ABI.** Logs, progress, errors, report entries and frame availability are polled. This keeps Python off native threads (research 01 G1-G2), keeps every input recordable, and keeps an out-of-process transport possible.
5. **Errors and faults.**
   - Every function returns `ar_status` (`AR_OK` = 0, then `INVALID_ARGUMENT`, `UNSUPPORTED`, `DEVICE`, `OUT_OF_MEMORY`, `ABI_MISMATCH`, `INTERNAL`); message text per handle from `ar_<object>_last_error`. Values come back through `AR_OUT` parameters.
   - **C++ exceptions** never cross the boundary: each entry point catches them and returns `AR_ERR_INTERNAL`. The engine never calls `abort` on bad input; a release assertion fails the session with a `SESSION_FAILED` entry.
   - **Structured exceptions** (access violation and the like) are not C++ exceptions. Every engine-owned thread body runs inside `__try/__except`, whose filter writes a minidump (`MiniDumpWriteDump`, system `dbghelp.dll`) beside the context log and **poisons the context**: every later call on it, its scenes and sessions returns `AR_ERR_INTERNAL` with "Engine fault, dump at <path>. Save to a new file and restart Blender." (memory may be corrupt, so not over the old file). On the calling thread, CPython's ctypes already turns a structured exception inside a foreign call into `OSError` (`Modules/_ctypes/callproc.c`); the extension treats that as a poisoned context. No process-wide handler (`SetUnhandledExceptionFilter`, vectored handlers) is installed (rule 8; Blender owns crash handling).
   - **Sticky CUDA errors** (illegal address, launch failure, launch timeout after a TDR, and the other errors CUDA documents as needing a process restart) cannot be recovered in-process, and the context is shared (D2.1). So CUDA is finished for the process: the session that hit it fails with `AR_ERR_DEVICE` and "GPU error: <text>. Save your work and restart Blender."; every other CUDA session fails at its next call; `ar_context_create` and `ar_session_create` on CUDA refuse with the same message. The CPU device keeps working. No engine flag is needed; CUDA's own state is what each context observes. This matches 0007 decision 44, and each occurrence counts toward D6 trigger (b).
   - Every session failure above is also recorded as a `SESSION_FAILED` report entry (D2.11).
   - **Log file.** `ar_context_create` takes a log path (the extension passes one under its user directory, the CLI one beside its output). Every line is handed to the OS as it is written, so lines before a crash survive a process death (not a power loss). Polling stays for the UI.
   - **Launch length.** Kernel launches are sized to 0009 B-17's target and hard cap (ruling 14), far below Windows' default TDR delay (B-17's basis); V14 measures the cap. The engine never changes TDR settings.
6. **Threading.** One handle is used by one thread at a time; different sessions may run concurrently. Long work runs on engine-owned native threads; calls return promptly except explicitly named wait calls. `ctypes.CDLL` releases the GIL for every call (research 08 §2).
7. **Versioning and identity.** Nothing is bumped by hand.
   - The generator (D2.10) computes **`AR_ABI_HASH`**, a `uint64_t`: the first 64 bits of SHA-256 over the normalised header (comments and whitespace removed). Any change to a function, struct, constant or annotation changes it.
   - It generates the struct layout table on the C side as `sizeof`/`offsetof` expressions, so MSVC computes the numbers and ctypes computes its own: two independent computations, not a hand-written twin.
   - Exported: `ar_abi_hash`, `ar_abi_layout` (per struct: name, size, alignment, field offsets) and `ar_build_info` (release version, git SHA, dirty flag, CUDA, OptiX, Embree and OIDN versions, build type, and the loose-kernel directory if a development build uses one). All three return `ar_status` and are `AR_QUERY`.
   - On load the extension and the CLI require the hash to equal `_abi.py`'s and every layout entry to equal ctypes' own; otherwise the engine is not registered and the error names the hashes or the struct field. The DLL, extension and CLI of one release are the only supported combination. **2.0 makes no cross-version ABI promise and offers no stable embedding API.** The check guards against stale binaries (the v1 stale-`.pyd` class).
8. **Device selection is explicit**, on `ar_context` (D2.1). The synchronous checks (no driver, driver below the floor, unsupported GPU, CPU without AVX2, CUDA dead after a sticky error) run in `ar_device_get_info`, which reports their status and reason, and in `ar_context_create`, which then fails with `AR_ERR_DEVICE` and that reason. Failures of the asynchronous device init a scene starts (module image missing for the GPU, OptiX module or pipeline; 0002 D15, 0007 decision 23) fail that scene's sessions with `AR_ERR_DEVICE` at their next call and a `SESSION_FAILED` entry. No silent CPU fallback (rule 7).
9. **Scope split.** 0001 sets the conventions, the handles and context creation (D2.1), the identity functions (D2.7), the context log (D2.5) and the report (D2.11). 0007 owns the render-control, scene-edit and film/pass/statistics readback function lists, a field list for every descriptor (`0007-appendix-abi.md`), and sync, threading and presentation; 0008 owns what the readback returns (0008 decision 13a); 0005 the material program format (ruling 33). All of them use the header, handle names and `ar_status` model above (ruling 10).
10. **Header grammar and annotations** (enforced by the generator, which is V2).
    - Allowed top-level forms: include guard, `#include <stdint.h>`, the `extern "C"` guard, `#define AR_<NAME> <integer literal>`, opaque handles `typedef struct ar_<name>_s* ar_<name>;`, `typedef uint64_t ar_key;`, POD structs per D2.2 (fields may be fixed arrays `T name[N]`), and prototypes `AR_API [AR_QUERY] ar_status ar_<object>_<verb>(...);`. Nothing else: no other macros, unions, function pointers or `char` except `const char*` strings.
    - Every pointer parameter or pointer field carries exactly one annotation (all expand to nothing in C):
      - `AR_IN`: `const T*` to one value read during the call; on `const char*`, a NUL-terminated UTF-8 string.
      - `AR_IN_ARRAY(n, T)`: `const T*` to `n` elements, where `n` names an integer parameter or field of the same call or struct; copied during the call.
      - `AR_OUT`: `T*` written by the call.
      - `AR_OUT_ARRAY(n, T)`: `T*` to a caller-owned array of `n` elements, `n` as for `AR_IN_ARRAY`, written by the call (readback, ruling 33); never recorded.
      - `AR_STAGED(n, T)`: `T**` receiving an engine-owned writable array of `n` elements from a `_begin` call.
    - `AR_QUERY` marks a function that only reads state (frame, log and report polling, progress, film, pass and statistics readback, `last_error`, identity, device lists).
    - **Recording rule:** the recorder (one per context, calls appended in arrival order under the recorder's lock) stores every non-`AR_QUERY` call with its `AR_IN`/`AR_IN_ARRAY` payloads, staged arrays captured at their `_commit`, and handles returned through `AR_OUT` as ids so replay can map them. Query results are never stored. Render control is input (0007 lists the calls). Replay executes the input calls in order, then renders each session to the sample count its settings request, or the count given on the CLI for viewport recordings, whose live progress depended on timing. Because an image-affecting edit starts a new epoch with a reset film (0007 decision 25, 0008) and the sampler is keyed on pixel, sample, dimension and seed with no stored state and no special seed value (0003), the result depends only on the inputs, which is what V11 needs.
11. **The per-render report.** The report tells the user, the CLI and the tests where the image differs from what the scene asks for, or what was not rendered (rule 7). One report per `ar_session`. Records raise only the codes in the table below; a new code is added by editing this table.
    - **Entry and summary** (in `astroray.h`):
      ```c
      typedef struct ar_report_entry {     /* 184 B, alignment 8 */
          uint32_t code;                   /* AR_REPORT_<NAME> */
          uint32_t level;                  /* AR_LEVEL_INFO 0, AR_LEVEL_WARNING 1, AR_LEVEL_ERROR 2 */
          uint64_t subject;                /* host key (0007) of the datablock concerned; 0 = scene-wide */
          uint64_t first_generation;       /* generation that first raised this key */
          uint64_t last_generation;        /* latest generation that raised it */
          uint64_t count;                  /* occurrences, in the unit the code names */
          double   value[2];               /* code-defined numbers, from the latest occurrence */
          uint8_t  detail[128];            /* UTF-8, NUL-terminated: node type, input, reason */
      } ar_report_entry;
      typedef struct ar_report_info {      /* 24 B */
          uint64_t revision;               /* changes whenever an entry is added, removed or changed */
          uint32_t entry_count;
          uint32_t highest_level;          /* AR_LEVEL_INFO when empty */
          uint32_t dropped;                /* distinct keys refused because the table was full */
          uint32_t pad0;
      } ar_report_info;
      ```
    - **Levels.** INFO: expected behaviour worth knowing. WARNING: the image differs from what the scene asks (magenta, approximation, clamp, bias, dropped samples). ERROR: something was not rendered, or the render could not proceed.
    - **Deduplication.** The key is (code, subject, detail). A session holds one entry per key; a repeat adds to `count` and updates `last_generation` and `value`. Kernels never write entries: they increment per-pass counters (0004 D29, 0006, 0008), and the host turns a non-zero counter into an entry when the pass is resolved. A material with an unsupported node is one entry however often it is shaded; a NaN in a million samples is one entry with `count` = 10⁶.
    - **Scope and lifetime.** Each code has a scope. SCENE: raised while a generation is built (sync, compile, validation, setup); removed when a generation that replaces or removes its subject, or follows `ar_edit_reset`, becomes active; scene-wide SCENE entries are recomputed with every generation. FILM: raised from render-time counters; cleared when the film resets (0008). SESSION: kept for the session's life, except `GENERATION_REJECTED`, removed when a later generation becomes active. The table holds at most 512 entries (PROVISIONAL); a further distinct key increments `dropped`, and existing keys keep counting.
    - **Polling.** Two `AR_QUERY` functions, never recorded:
      ```c
      AR_API AR_QUERY ar_status ar_session_report_info(ar_session s, AR_OUT ar_report_info* info);
      AR_API AR_QUERY ar_status ar_session_report_entry(ar_session s, uint32_t index, AR_OUT ar_report_entry* entry);
      ```
      `report_info` snapshots the table for that handle; `report_entry` reads entry `index` of the latest snapshot (`AR_ERR_INVALID_ARGUMENT` past the end). A snapshot is ordered by level (descending), code, subject and detail, so equal states read identically. A host polls `report_info` whenever it polls progress and reads entries only when `revision` changed. The addon shows each key once per render; 0007 decision 38 owns the presentation, and host-side diagnostics found in Python (0007 decisions 15, 17, 20, 22, 47) are listed beside the engine's entries without engine codes. The CLI prints the final table and writes it to the log, and `render` exits non-zero if any ERROR entry exists. Tests read the same functions; 0008 and 0009 decide which codes fail a test.
    - **Codes.** Generated into `astroray.h` as `AR_REPORT_<NAME>`, numbered in table order from 1 (no cross-version meaning, D2.7).

### D3. Platform and hardware

1. **OS:** Windows x64 only. Windows 11 is tested; Windows 10 x64 is neither tested nor refused.
2. **Blender:** 5.3.x, manifest `blender_version_min = "5.3.0"`, no `blender_version_max` (owner decision 3; D9.4 removes the OIDN coupling that would need one). Supported GPU backend: Vulkan, Blender 5.3's default (research 01 A2, spike B). OpenGL is 0007's call.
3. **GPU (tested):** RTX 5070 Ti, sm_120, the only tested hardware.
4. **GPU (built):** release builds contain SASS for sm_75, sm_86, sm_89 and sm_120, plus compute_120 PTX. Compute capability 7.5 (Turing) is the floor: it has RT cores, it is the CUDA 13 floor, and it is the DLSS-RR floor (research 08 §1; research 10). Other generations are untested and the release notes say so. `check full` compiles all four architectures (V13), so failures there appear before a release build. The owner accepts these untested builds, labelled so (owner decision 29).
5. **Driver floor:** R590, which the pinned OptiX (0009 decision 2) requires (research 08 §6, research 03 F5), checked by device enumeration and context creation, which refuse with `AR_ERR_DEVICE` naming the found and required driver (D2.8). The DLSS mode's own floor belongs to 0008 and spike F.
6. **CPU:** x86-64 with AVX2 (ruling 15). The CPU device's code (kernels and CPU stages) is compiled with `/arch:AVX2`; the rest of the host code stays at the baseline, so the DLL loads on any x86-64 machine and a CPU without AVX2 (`IsProcessorFeaturePresent(PF_AVX2_INSTRUCTIONS_AVAILABLE)`) gets the CPU device refused with a reason (D2.8) instead of an illegal-instruction fault. Embree dispatches its own ISA. Spike A §4/§7 measured the baseline build; CPU/GPU agreement of the AVX2 build is re-measured by 0009's agreement ladder.
7. **What end users install:** Blender 5.3 and, for GPU rendering, an NVIDIA driver R590 or newer; the CPU device needs AVX2. No CUDA toolkit, OptiX SDK, Python packages or VC++ redistributable. The DLL loads and offers the CPU device on a machine with no NVIDIA driver: cudart is static and loads `nvcuda.dll` dynamically.

### D4. Language and toolchain

1. **Language:** C++17 for host code and kernels; kernel code is spine §2's restricted subset behind 0002's host/device macro layer. C11 subset for `astroray.h`. Python 3.13 for the extension and build-time tools. Tools (the ABI generator: stdlib only; scene builders: stdlib + NumPy) run on **Blender's bundled `python.exe` and NumPy** with `-I`, with no separate Python toolchain or virtual environment (ruling 32); versions and the hosted-CI Python are pinned in 0009 decision 2 (ruling 31). MEASURED: spike A built all 34 GPU translation units and the CPU target with `-std=c++17`.
2. **Compilers** (versions pinned only in 0009 decision 2, ruling 31): MSVC `cl` for host code and the CPU target; nvcc from the CUDA toolkit for all GPU code, ahead of time, with no runtime compilation path (ruling 16); CMake + Ninja, one build tree (spine §9). No clang-cl, no MinGW: nvcc on Windows accepts only MSVC as host compiler (research 08 §1). The two targets use different compilers on one source: nvcc's own front end and cicc for device code, MSVC for the CPU target and host stubs. Their agreement is measured, not assumed: 1.1e-6 max eval error with `-fmad=false` (spike A §6). MEASURED, spike A §1/§4/§5: nvcc 12.8 accepts MSVC 19.44 with `sm_120`; the full build, per-TU and CPU-target times are the basis of 0009 B-01, B-05 and B-08.
3. **CUDA version policy.** Stay on 0009's pinned 12.x toolkit until a 13.x toolkit passes spike A's `run_all.ps1` (registers, compile seconds, runtime, CPU/GPU agreement) with no gated number regressing above 10%; the move lands as a superseding note.
4. **CRT and runtime linkage:** `astroray_core.dll`, `astroray_cli.exe` and our OIDN build use the static CRT (`/MT`) and static cudart, so nothing depends on the VC runtime Blender bundles (research 08 §2, option B). Safe because no CRT object crosses the C ABI (D2.3). Fallback if `/MT` fails to link: `/MD` with a toolset no newer than Blender 5.3's shipped runtime, **14.44.35211** (measured, Context); the local 19.44.35208 qualifies. (Research 08's 19.44.35216 is Blender's minimum *build* toolset, which is newer than the runtime it ships.)

**Why not Slang.** Its case was compile speed and modularity, and spike A shows C++ already meets 0009's compile budgets B-01 and B-05 (measured; their basis column), where v1's slowest TU exceeded B-05 by orders of magnitude. Slang's CUDA and OptiX route still ends in NVRTC and ptxas (research 03 F2), so it cannot change register allocation or ptxas time. Its CPU targets lack user atomics and ray queries, its LLVM target is "highly experimental" with open internal compiler errors (research 03 F3; issue #13705 open), and it ships breaking changes monthly. Slang was not run in spike A, so this record does not claim it is slower; it has no gap left to close and adds risk to the CPU oracle. The time-boxed Slang comparison in CHECKPOINT-1 is dropped.

**Why not Rust.** No Rust route reaches OptiX: wgpu ray tracing is experimental with no SER, cuda-oxide is experimental 0.2 with Windows lagging, Rust-GPU has no ray-tracing evidence (research 03 F7). Kernels would stay C++/CUDA, so host and kernel would be two languages. Owner decision 2 needs the CPU target to compile the same kernel source, which takes a C++ compiler; every dependency (CUDA, OptiX, Embree, OIDN) is a C or C++ API. Rust compile times were not measured.

### D5. NVIDIA first and the single vendor seam

1. CUDA kernels do the shading; OptiX 9.1 does GPU traversal only. Embree 4 does CPU traversal, and a CPU thread pool runs the CPU stages. No AMD, Intel or Apple backend is built or tested in 2.0 (research 03 F4: Vulkan RT gives an add-on no interop advantage; Blender itself uses per-vendor ray-tracing libraries).
2. **The vendor seam is one host interface, `Device`,** with `CpuDevice` and `CudaDevice`: memory (allocate, free, upload, download); stage launch over a work count, with streams and events; traversal (per-mesh bottom-level and instance top-level structures; closest-hit and any-hit over a structure-of-arrays ray batch; curved-ray segments are ordinary rays with a `tmax`, spine §3); identity and capability queries. Dispatch is per launch, never per ray. Vendor-specific code lives only in `src/device/cpu/`, `src/device/cuda/`, `src/kernel_gpu/`, 0002's kernel portability header and the DLSS backend in `src/denoise/dlss/` behind 0008's denoiser interface. Include rule (ruling 39): CUDA and OptiX headers only in `src/device/` and `src/kernel_gpu/`, Embree headers only in `src/device/cpu/`, NGX headers only in `src/denoise/dlss/`. Traversal is the only vendor-specific *algorithmic* code. Another vendor would mean a third `Device` plus one portability header, as in Cycles (research 03 F1); the interface costs nothing beyond what the CPU target already needs.
3. DLSS Ray Reconstruction is an optional NVIDIA viewport mode, loaded from the driver, never bundled (spine §8; research 10). OIDN is the default denoiser.

### D6. Process model

The engine runs **in-process** inside Blender as a ctypes-loaded DLL with engine-owned native threads. MEASURED (spike B; mesh and instance sync only, no shader, texture or light sync, no rendering): the Python overhead per present is negligible and a synthetic native producer (no rendering) held 24, 30, 60 and 120 updates/s at 1080p on the B16 path, which bounds the present cost only (§1.1-§1.2; numbers in 0009 B-13's basis); first frame for 5.04 M triangles in 10,001 instances on the fast read path is **1.1x** Cycles' F12 pre-first-sample and **1.5x** Cycles' viewport sync-to-first-sample (§3). Spike B §4: "not yet a pass for the full product".

**Owner decision 9 is therefore unproven.** The measured part sits within 0007's first-frame gate (ruling 21) against F12 and at its edge against the viewport; material, texture and light sync and the cost of rendering while presenting are unmeasured, and 0007 owns them. In-process is chosen anyway because its measured transport cost is negligible and every alternative adds a copy and a protocol on top.

An out-of-process daemon stays a fallback, adopted only by a superseding record if: (a) a third-party DLL conflict with Blender cannot be fixed under D9.4; (b) 0007's coexistence soak (its V13, pass criterion zero) records an engine-caused Blender crash, poisoned context or sticky CUDA error (D2.5) that a fix in process cannot remove, or GPU faults prove frequent in the field, which is the lead's call (owner decision 29); (c) concurrent sessions cannot be kept clean. D2.4 keeps the ABI transportable.

### D8. Data policy

1. **In the repository and the extension:** data under CC0 or public domain, data under a permissive licence with recorded provenance, and tables we generate. Examples: Jakob-Hanika tables regenerated from `rgb2spec_opt.cpp` (BSD-3 in mitsuba-renderer/rgb2spec, Apache-2.0 in pbrt-v4; research 11 §5-§6) rather than copied as a blob of unclear licence; refractiveindex.info (CC0, cite Polyanskiy 2024); energy-compensation tables (such as GGX albedo) computed by our own tools. A third-party table generator is used only after its licence is read and recorded.
2. **CIE data.** The CIE publishes the 1931 colour-matching functions as an open-access dataset with no licence stated; a CIE webshop notice says "other distributors are not authorized" (research 11 line 128). A redistributor's licence (pbrt-v4 Apache-2.0, colour-science BSD-3) covers its code, not the CIE's terms on the values. 0003 takes the values from pbrt-v4 at a pinned commit, records that provenance and the dataset DOI, and never labels them "public domain". Shipping them is an accepted, recorded risk pending owner question 5.
3. **Never in the repository or the extension:** NIST ASD (rights reserved), CHIANTI (terms not stated), ExoMol (CC BY-SA; derived tables are likely adaptations), Cloudy outputs.
4. Every shipped data file has an entry in `data/MANIFEST.toml`: SPDX id or URL, citation, version, SHA-256 and the generating command. Generated tables are **committed** and embedded at build time; their generators are not in the default build target (0003 decision 18), so a clean build never runs them.
5. **Data packs** are separate zips on GitHub Releases, each with its own licence and manifest, installed by choosing a directory in the extension preferences. The engine rejects a pack whose manifest is missing or whose hash does not match, with a visible error. The extension declares no `network` permission and downloads nothing.

Kernel headers include none of these except where 0002 and 0006 allow NanoVDB. Any other library goes through D9.6.
2. **How dependencies are obtained** (research 08, recommendation 11):
   - Header-only code is vendored under `third_party/<name>/` with LICENSE and VERSION files.
   - Binaries and NVIDIA headers (our Embree and OIDN builds, the OptiX headers tag, the NGX headers) are fetched by the dependency script (0009) into a git-ignored cache, pinned by URL and SHA-256; a mismatch is a hard error.
   - Where no suitable upstream binary exists (Embree without TBB; OIDN with a renamed library, static CRT and static oneTBB), we build once with a recorded script and publish the archive as a release asset of our repository; that build is not part of the normal build (ruling 12). Tools that only this script needs (ISPC for OIDN) never enter the clean build.
   - No vcpkg, no FetchContent, no network during configure. A clean build compiles only Astroray's own code.
3. **Excluded:** GPL and LGPL code in the core; any shared TBB (`tbb12.dll` is Blender's; research 01 I1, BlendLuxCore crash precedent); upstream prebuilt OIDN (its CPU device imports `tbb12.dll` and all its modules use the dynamic VC runtime, as Blender's 5.3 copy shows); Python headers, pybind11, nanobind, USD, MaterialX, OpenColorIO, Vulkan SDK components; NVRTC (ruling 16); any NVIDIA RTX SDK binary.
4. **No module-name collisions with Blender.** No DLL in either zip shares a base name with any DLL Blender ships or loads (measured list in Context). Renaming OIDN's modules makes this independent of Blender's OIDN version, so 5.4 changing OIDN needs no action and no load-time version check. V5 verifies it with OIDN loaded. If oneTBB cannot be linked statically into the OIDN CPU device, that device is left out, CPU-device renders report `DENOISER_UNAVAILABLE` with "denoiser unavailable on the CPU device" (rule 7), and binding to Blender's `tbb12.dll` instead needs a superseding note with V5 evidence.
5. **The extension** depends on Blender's bundled Python, NumPy and `ctypes` only.
6. **Adding a dependency** requires a `THIRD_PARTY.md` entry naming licence, version, SHA, purpose, the feature and record that need it, and its measured cost: clean-build seconds, DLL size, load time when unused. A dependency whose unused cost is not near zero is lazy-loaded.

### D10. Packaging, releases and distribution

1. **Versions.** Semver. Pre-release builds are `0.<n>.<patch>` GitHub pre-releases (milestones in `docs/ROADMAP.md`); the first full release is `2.0.0`. `AR_ABI_HASH` is independent of the release version.
2. **Artifacts per release**, all from one clean build on the lead's machine via `tools/release.ps1`:
   - `astroray-<ver>-windows-x64.zip`: the extension, built with `blender --command extension build --split-platforms`. Manifest: `id = "astroray"`, `platforms = ["windows-x64"]`, `license = ["SPDX:GPL-3.0-or-later"]`, no "Blender" in the name. Holds the extension code, `astroray_core.dll` (kernels and tables embedded), the `astroray_oidn*` DLLs, LICENSE-APACHE, LICENSE-GPL, `THIRD_PARTY.md` and `BUILDINFO.txt` (toolchain versions, git SHA).
   - `astroray-cli-<ver>-windows-x64.zip`: the CLI, the same DLL, the same OIDN DLLs (so the CLI and tests can denoise), licences.
   - `SHA256SUMS`, and release notes stating which hardware was tested. Binaries are not code-signed in 2.0.
3. **Channels:** GitHub Releases on the owner's public repository host the zips. A self-hosted Blender extension repository (static JSON index generated by Blender's extension tooling, served from GitHub Pages) lists every release; users add its URL once and get updates through Blender. No listing on extensions.blender.org: its ToS 3.6 forbids precompiled packages (research 11 §1).
4. **Release gate.** `release.ps1` refuses to publish unless the full test gate passes (0009), V1-V7 and V12-V15 pass, and the zip installs into an isolated clean Blender 5.3 profile (spike B's `BLENDER_USER_*` isolation), enables, and renders the smoke scene on both the CUDA and the CPU device.
5. **Updating.** Blender locks a loaded DLL. Updating or uninstalling while the extension is loaded is unmeasured (research 08's spike S5 never ran); V12 tests it. Until V12 passes, the release notes say: disable the extension, restart Blender, then update.
6. **Size.** PROVISIONAL budget: extension zip at most 150 MB. Reference: upstream OIDN's prebuilt zip is 56.6 MB (research 10 §6); Blender's `OpenImageDenoise_core.dll` alone is 47 MB.

### D11. Out of scope for 2.0

- macOS, Linux and Windows ARM64; AMD, Intel or Apple GPUs and any HIP, Metal, SYCL or Vulkan-compute backend; multi-GPU and distributed rendering.
- A Hydra delegate, USD or MaterialX import, plugins for other DCCs; a Blender fork or patch, and zero-copy display (owner decision 14; research 01 F4).
- An out-of-process daemon, except through the D6 gate; in-process CUDA recovery after a sticky error.
- Slang, Rust, Dr.Jit, nanobind, pybind11 and runtime kernel compilation; Python wheels and PyPI; a stable embedding API or ABI, and a version-independent scene file format.
- An extensions.blender.org listing, in-addon downloads, code signing, commercial licensing and a CLA; redistributing any NVIDIA binary; Blender before 5.3.

## Alternatives considered

| Alternative | Evidence against |
|---|---|
| Slang kernels | D4: C++ meets the budgets (spike A); weak CPU target, monthly breaks (research 03 F3); same ptxas (F2). |
| Rust host or kernels | D4: no OptiX route, so two languages (research 03 F7). |
| Dr.Jit | Symbolic mode recreates the megakernel register problem; weak Windows debugging (research 03 F6). |
| Vulkan RT, vendor-neutral | No interop gain for an add-on (research 03 F4); curves NV-only; one NVIDIA GPU to test; untested vendor paths conflict with "fail loudly". |
| nanobind or abi3 `.pyd` (research 01, rec. 3) | Spike B: 0.014-0.03 ms Python overhead per present through ctypes. nanobind adds a Python-version axis, `/MD` and the wheel-rule question (research 01 J2). |
| Out-of-process daemon (research 01 option c) | Protocol, lifecycle and start-up cost on top of a measured-negligible transport. Kept as the D6 fallback. |
| Hydra delegate | USD rebuild per Blender release, lossy RGB materials, no per-object astrophysics data (research 01 H5, H7). |

| Separate scene format for the CLI | A second format to version. Recording ABI inputs is the same data at no extra design cost. |
| Free-text message queue for the report | Repeats arrive once per occurrence (a NaN per sample), tests would match on prose, and the "listed once per render" rule would live in every host. Keyed entries with closed codes deduplicate in one place and are testable by code. |

| TBB-linked prebuilt Embree | Name collision with Blender's `tbb12.dll` (research 01 I1). |
| vcpkg or FetchContent | Network access and source builds during configure (research 08, option G). |
| GPL or MIT core | Owner decision 5; GPL would also conflict with the NVIDIA clauses (research 11). |
| extensions.blender.org | ToS 3.6 forbids precompiled packages (research 01 J3). |
| `/MD` CRT | Ties every build to Blender's bundled runtime (research 08 §2). Kept as the fallback. |

## Consequences

**Made easy:** one DLL serves Blender, the CLI and tests, and the hash check removes the v1 stale-binary class without a human step. Recordings turn any Blender scene into a deterministic fixture and make bug reports reproducible without Blender. Struct layouts, bindings, recorder and replayer come from one header. One report with closed codes serves the UI, the CLI and the tests. One kernel source serves both targets, with agreement measured. End users install nothing beyond Blender and a driver. Agents work against mechanical rules (grammar, annotations, POD structs, no callbacks, status codes, report codes) that scripts check.

**Made hard:** no device other than NVIDIA; a port costs a `Device` plus a portability header. Recordings are bound to one ABI hash, so canonical scenes are regenerated from builders or `.blend` files (0009). A fault on an engine thread no longer kills Blender at once but poisons the context; a GPU fault ends GPU rendering until Blender restarts; a fault in Blender-side code still takes Blender down. Updating the extension needs a restart until V12 says otherwise. No runtime compilation anywhere, so every kernel variant is compiled ahead of time (suits spine §2's runtime flags). Four GPU architectures cost about four times the device compile, in `check full` and release builds only. A CPU without AVX2 gets no CPU device. Every new diagnostic needs a code in D2.11. We maintain two recorded dependency builds (Embree, OIDN).

**Cost when a feature is unused:** OIDN: zip size only, loaded on first denoise. DLSS: nothing unless enabled. Recorder: one predictable branch per ABI call. Log file: one buffered write per log line. Report: nothing until an entry is raised; one keyed lookup per raised occurrence, and kernels only increment counters they already keep. `__try` frames: none on the no-fault path (table-based on x64). CPU device: binary size and spike A's 0.65 s compile. `Device` dispatch: one indirect call per launch. Data packs: nothing unless installed.

## What lands when

Milestones and their contents live only in `docs/ROADMAP.md` (G1).

**Must exist from the first milestone, because retrofitting is expensive:**
- `astroray.h` in the D2.10 grammar with the generator for `_abi.py`, the layout table, the hash, the recorder and the replayer: every later function is written against it, and adding it later means rewriting every binding and re-recording every fixture.
- The handle model, `ar_status` on every function and no callbacks (D2.1-D2.6): changing any of them later changes every signature in the header.
- The report schema, codes and polling (D2.11): every record raises codes; bolting it on later means revisiting every diagnostic site and every test that should fail on one.
- The fault handling of D2.5 with the log file: every engine thread body and entry point is written around it.
- `/MT` with static cudart, Embree without TBB, our renamed OIDN build, and the no-collision rule checked by V5 with OIDN loaded: a DLL conflict found late can force the process-model change of D6 (a).
- `CpuDevice` and `CudaDevice` behind `Device` (D5.2): owner decision 2 needs both from the first kernel, and a CPU device added later would inherit CUDA assumptions.
- Release kernels and tables embedded in the DLL, with `ar_build_info` (D1.1, D2.7): the v1 stale-artifact class appears with the first loose file.
- SPDX headers, per-directory LICENSE files, `THIRD_PARTY.md` and `data/MANIFEST.toml` (D7, D8.4): the repository is public from the start, and auditing provenance after the fact is far harder than recording it.

**Can be added later without redesign:**
- The DLSS mode (if spike F passes), behind 0008's denoiser interface.
- `release.ps1`, the GitHub Pages index, the size check and the release-only checks V7 and V12.
- The data-pack loader (D8.5).
- A smoke test on a Blender 5.4 beta once available, with any break raised as a superseding record.
- CUDA 13.x (D4.3) once it passes.
- Another `Device` (D5.2), only if the owner asks; code signing.

## Risks and open items

1. **Static oneTBB inside our OIDN CPU device** is untested (OIDN documents `OIDN_LIBRARY_NAME` but no static-TBB option; oneTBB discourages static builds). Settled by V5; fallback in D9.4.
2. **A raw DLL inside an installed extension** is unmeasured; spike B registered its add-on from a `--python` script. V5 runs from an installed zip. If Blender's installer rejects it, the fallback is a wheel containing the DLL, which raises the "unmodified from PyPI" question (research 01 J2).
3. **`/MT` with static cudart, our Embree and our OIDN builds** is not yet linked together. Fallback in D4.4.
4. **Continuing after a structured exception** can leave Blender's memory corrupt; the message tells users to save to a new file. If 0007's coexistence soak (its V13) shows corrupted saves, poisoning becomes termination via the D6 gate.
5. **CUDA 12.8 vs 13.x.** All evidence is from 12.8; Blender 5.3's Cycles moved to CUDA 13 (research 10). No conflict expected: cudart is static and the driver is shared.
6. **First launch after install or a driver update** compiles OptiX modules on the user's machine once per driver (spike A §5; 0009 B-18's cold limit). 0002 decides the module count; it is measured against 0007's first-frame gate, which D6 records as unproven.
7. **OptiX licence pass-through** (DesignWorks 1.1(ii)(b)) for compiled modules in an open-source product is unresolved; Blender ships the same pattern (owner question 2).
8. **Spike A is a lower bound.** Full-scope compile times are unmeasured; 0002 and 0009 own the gate. C++ stands unless a budget breaks and a different language would provably fix it, which research 03 F2 makes unlikely for any NVIDIA route.
9. **Recordings are bound to one ABI hash**, so a bug report must come from the same release; `ar_build_info()` is in every recording and the CLI's printed report.
10. **Blender 5.4** may change the RenderEngine or `gpu` surface; the 5.3/5.4 boundary files were identical on 2026-11-14 (research 01 K1). Checked by the 5.4 beta smoke test.
11. **AVX2 build unmeasured.** Spike A measured the baseline CPU build; `/arch:AVX2` may change CPU/GPU agreement through contraction and vector maths, which 0009's agreement ladder checks. (The previous revision's conflicts with other records are settled by `RULINGS.md`.)

## Challenges to the spine

1. **Spine §1, "the traversal interface is the only vendor seam".** Read literally this is not achievable: memory, launch, streams and events are also CUDA-specific. Cycles keeps one device class per backend (research 03 F1). This record makes the seam the `Device` interface, with traversal the only vendor-specific algorithmic code (D5.2). Intent unchanged; wording should change.
2. **Spine §1, "versioned C ABI".** Defined here as a generated header hash used as an exact-match stale-binary guard with no cross-version compatibility (D2.7; ruling 10). A narrowing, not a reversal.
3. **Spine §6** says "60 updates per second held" and quotes 1.42 s against 1.28 s without caveats. The 60/s came from a synthetic producer with no rendering, and against Cycles' viewport the first frame is 1.5x with shader, texture and light sync omitted (D6). The spine should carry those caveats.

## Review and resolution

History of the independent review; the Decision section and the Reconciliation section below supersede it where they differ.

1. Sticky CUDA error: ACCEPTED. D2.5 now says CUDA is finished for the process, the UI says restart Blender, the CPU device keeps working, and it counts toward D6 (b). D1.4 makes the CLI and the test executables the main development host. Added V14 and an alternatives row.
2. ABI versioning: ACCEPTED. `AR_ABI_HASH` is a SHA-256 of the normalised header. The layout table is generated as `sizeof`/`offsetof`, so MSVC and ctypes compute it independently. A separate function-signature table was not added, because the hash already changes on any signature change (V1 tests this). Its only gain would be naming the function, and the remedy, a rebuild, is the same.
3. Generated binding and recorder: ACCEPTED. D2.10 defines the grammar, the annotations `AR_IN`/`AR_IN_ARRAY`/`AR_OUT`/`AR_STAGED`/`AR_QUERY`, the recording of inputs only, and replay to N samples. V2 and V11 are updated.
4. OIDN: ACCEPTED, with a different remedy. dumpbin on Blender 5.3's copy confirms the CPU device imports `tbb12.dll`. We now use our own OIDN build with renamed modules, static CRT and static oneTBB, shipped in both zips and required from the start with V5. The Blender OIDN version check at load time was not added: renamed modules make Blender's OIDN version irrelevant.
5. D6 evidence: ACCEPTED. Both ratios (1.1x and 1.5x) are quoted, the caveats on synthetic present and omitted sync are stated, and owner decision 9 is recorded as unproven. Spine challenge 3 is added.
6. Failure handling: ACCEPTED. D2.5 adds the per-context log file, `__try/__except` with a minidump on engine threads and no global handler, ctypes' `OSError` on the calling thread, and a launch limit under TDR. The last is a constraint on 0002 and 0004; its numbers are now 0009's (ruling 14).
7. "Single front end": ACCEPTED. D4.2 and "Why not Rust" are reworded around owner decision 2 and the measured `-fmad=false` agreement.
8. Multi-architecture compile: ACCEPTED in substance. The compile runs in `check full` on demand (V13); nothing is scheduled (G3).
9. Citations: ACCEPTED, all five. The Cycles per-file licences are stated. The CIE terms are restated and made owner question 5. The LTC example is removed, and third-party generators need a recorded licence. 35216 is corrected to the measured shipped runtime 14.44.35211. The DLSS floor is deferred to 0008 and spike F.
10. Interpreter and `_abi.py` licence: ACCEPTED. Blender's bundled `python.exe` runs the tools (D4.1), and `_abi.py` carries Apache-2.0 (D1.3, D7.1, V4).
